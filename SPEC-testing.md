# Resid Test Framework

**Status: design document with an implementation ledger.** The normative
language rules live in `resid_specification.txt`; this file states what a
test framework for Resid is and, section by section, how much of it exists.
Every example below is Resid as the compiler accepts it (see §0), and every
status claim is checked by `tests/pkg/run.sh` or a conformance case named in
the row.

Related: `resid_specification.txt` §1016 makes a `test` block an entry point
for the purpose of capability authority; §24 lists `assert`; §37 lists the
tooling surface.

## Vision

First-class testing built into the language: tests are compiled, not
interpreted; a test is an ordinary program whose entry point is generated by
the compiler; and the framework is discoverable at compile time.

---

## 0. Notation and current syntax

Earlier drafts of this file were written in a Rust-like pseudo-syntax
(`fn add(a: Int, b: Int) -> Int`, `var`, `|| {}`, `#[attr]`, `Fn(A, B) -> R`).
None of that is Resid. The real forms, all of which the compiler accepts:

| Concept | Resid syntax |
|---|---|
| Function | `Int add(Int a, Int b) { return a + b; }` |
| Parameter | `Int a` — type first |
| No assignment | bindings are immutable; shadowing is forbidden (§7) |
| Closure literal | `lambda(a, b) { a + b; }` |
| Closure type | `Int closure(Int, Int)` — *not* `Fn(Int, Int) -> Int` |
| Annotation | `@requires(filesystem(readonly))` — *not* `#[...]` |
| Sum case | `None`, not `null` |
| No blocks/impls | no `type X = { ... }` methods; behaviors are external (§11) |

## 1. Test Syntax

### 1.1 Inline Test Blocks — implemented

A `test` block is a top-level declaration with a display name and a body. The
compiler discovers it at compile time, rewrites it to a plain function, and
generates the entry point that calls it.

```resid
Int add(Int a, Int b) { return a + b; }

test "add: identity" {
    expect(add(0, 5)).toEqual(5);
    expect(add(5, 0)).toEqual(5);
}

test "add: commutativity" {
    expect(add(2, 3)).toEqual(add(3, 2));
}
```

Enforced by the compiler:

- a test file may not define `main` — the entry point is generated
  ("a test file's entry point is generated")
- a test file with no `test` block is rejected ("no `test "..." { ... }`
  blocks found")
- a `test` used as an ordinary identifier inside a function body is not a
  block; discovery walks declarations, not tokens

Implementation: `td_scan`/`td_desugar` and `td_main_ir` in
`compiler/driver.resid`. Cases: `tests/conformance/cases/` (the framework's
own behavior), `examples/math_test.resid`.

### 1.2 Test Files (`*_test.resid`) — implemented

The naming convention is `*_test.resid`. Discovery is by suffix; there is no
`test_module` block and no `register` function in the block form:

```resid
// src/math_test.resid
import "mathlib.resid";

test "add: identity" {
    expect(add(0, 5)).toEqual(5);
}
```

An earlier draft specified `test_module "math" { register(...) }`. That form
is **not** implemented and is not planned; §1.3 covers registration.

### 1.3 Explicit Registration — implemented

For a suite assembled as data — a table of cases built by a loop, or cases
from a library — `lib/testing.resid` registers cases explicitly and runs them
in one binary. This is what `test` blocks cannot express.

```resid
import "testing.resid";

Int add(Int a, Int b) { return a + b; }

Int main() {
    List(TestCase) cases = [
        test_case("add: identity", lambda() { expect(add(0, 5)).toEqual(5); }),
        test_case("add: zero",     lambda() { expect(add(0, 0)).toEqual(0); })
    ];
    return run_tests("math", cases);
}
```

`run_tests` returns the process exit code (0 all passed, 1 any failure) and
honours `RESID_TEST_FORMAT` and `RESID_TEST_FILTER`, exactly as `residc test`
does. `property_case` exists and records the intent, but generates nothing
(§3).

### 1.4 Test Attributes — not implemented

`#[test]`, `#[test_property]` and `#[test_suite(parallel = false)]` are not
Resid syntax and do not exist. Per-test metadata is expressed with ordinary
Resid: a capability-needing test declares `@requires` on the block itself.

```resid
@requires(filesystem(readonly))
test "reads the config" {
    expect(filesystem.exists("config.toml")).toBeTrue();
}
```

## 2. Assertions

### 2.1 Matchers — implemented

`expect(value)` wraps a value of any type in `Expect(T)`, a builtin generic
container. The checker types the matcher against `T`, so a mismatch is a
**compile error**, not a runtime one:

```resid
expect(2 + 2).toEqual(4);
```

```text
error[E0001]: type error: call toEqual expects (Int), got (Str)
  --> bad_test.resid:2:57
2 |     expect(twice(21)).toEqual("not an int");
                                                          ^^^
```

**Every matcher is an assertion returning `Void`.** None of them is a
predicate, so none can be assigned, interpolated into an f-string, or
negated with `!`. A test states what must hold, not what it holds.

| Matcher | Checks | Arity |
|---|---|---|
| `toEqual(v)` | equal value, T-aware | 1 |
| `toBe(v)` | same as `toEqual` | 1 |
| `toNotEqual(v)` | different value | 1 |
| `toBeTrue()` | a `Bool` that is true | 0 |
| `toBeFalse()` | a `Bool` that is false | 0 |
| `toBeNull()` | an `Option` is `None` | 0 |
| `toContain(x)` | a list holds `x` | 1 |
| `toHaveLength(n)` | a list or string length | 1 |
| `toMatch(re)` | a string matches a regular expression | 1 |
| `toBeCloseTo(x, tol)` | a `Float` within `tol` | 2 |
| `toThrow()` | the given closure aborts | 0 |
| `toSatisfy(pred)` | the predicate holds | 1 |

`toBeCloseTo` is **Float-only**. An earlier draft documented an `Int` form
("equal to `n` decimal digits"); the compiler rejects it
(`toBeCloseTo expects Expect(Float)`).

`toThrow` takes its closure from a **typed binding**, not an inline literal,
because an inline `lambda` has no expected type to conform to:

```resid
Void closure() f = lambda() { expect(1).toEqual(2); };
expect(f).toThrow();
```

`toSatisfy` takes **one** argument. An earlier draft documented
`toSatisfy(pred, why)`; the compiler rejects the second
(`toSatisfy takes 1 argument`). Pass the reason as a comment.

`toBeNull` is the only name that refers to absence; there is no `null`
literal in Resid (§14).

### 2.2 Rich Diffs — partial

A failing equality prints both sides and, for a failing `toHaveLength` or
`toContain`, the collection involved:

```text
✗ deliberately fails (0ms)
  expectation failed: toEqual
      actual:   2
      expected: 3
```

A general structural diff of arbitrary composites, and per-type formatting
of nested values inside the diff, are not implemented.

### 2.3 Custom Matchers — not implemented

There is no way to define a matcher. A check that is not in the table above is
an ordinary function returning `Void` that calls `assert` (§24).

## 3. Property-Based Testing — not implemented

Generators, `forall` bindings, shrinking, and `--max-cases` / `--max-shrinks`
do not exist. `lib/testing.resid` provides `property_case`, which records the
name and body and runs it as an ordinary case; it generates nothing. This is
the largest specified-but-absent area, and the one that most needs a design
decision (a generator is a function from a seed to a value, which the
reduction model makes interesting but expensive).

---

## 4. Comptime Discovery

### 4.1 Collection — implemented

Discovery is a compile-time rewrite of the merged source: each
`test "name" { … }` becomes a `Void restestN()` function, the display names
are collected in order, and a generated `main` calls
`resid_test_plan(n, module)`, then `resid_test_run` per test, then
`resid_test_summary` to decide the exit code. Nothing is interpreted.

`TestInfo` as a struct with `module`, `tags`, `is_property` and
`property_config` fields is **not** implemented; the generated entry point
carries names and symbols as parallel lists.

### 4.2 Filtering at compile time — partial

Filtering is applied at **run** time, by the generated runner reading
`RESID_TEST_FILTER`, not at compile time: an unmatched test is still
compiled and still linked. A compile-time filter would let reduction and
lowering drop it entirely, which is the more Resid-shaped answer and is not
implemented.

---

## 5. Test Runner

### 5.1 Execution mode — serial

Tests within a file run in declaration order, one at a time. A
`SuiteConfig` with an execution mode, a parallelism limit and a per-test
timeout is not implemented.

### 5.2 A sandbox per test — not implemented

There is no per-test `sandbox`. Authority is per *function*: a test block
that needs a capability declares `@requires` on itself (§1.4), and the
enclosing program's or sandbox's ceiling still bounds it. That is a stronger
statement than a per-test sandbox — the capability is checked, not merely
supplied — but it is not the same mechanism.

### 5.3 Parallel execution — not implemented

Execution is serial. `spawn` regions exist (§19) and would be the natural
mechanism, but aggregating results across threads is not built, and a
parallel runner would need the §5.4 result type to be collectable.

### 5.4 Result type — partial

The runtime tracks a pass/fail count and prints a summary; it does not build
a `TestResult` per test with a status, duration, failure message and diff.
`Skipped`, `Timeout` and `Panic` as statuses do not exist: a test either
passes, fails an assertion, or the process aborts.

---

## 6. Snapshot Testing — not implemented

No `expect_snapshot`, no snapshot storage, no snapshot diffing.

## 7. CLI Interface

### 7.1 Commands — implemented

```text
residc test                          # every *_test.resid under --root (default ".")
residc test <file.resid>             # one file
residc test --root src               # every *_test.resid under src
residc test --filter REGEX           # run matching tests
residc test --format pretty|tap|json # report format (default pretty)
```

Driver flags that reach a test run: `--root DIR` (discovery root),
`--testbin-dir DIR` (where per-file test binaries are written; default
`target/resid`), `--filter RE`, `--format F`, plus the ordinary build flags
`-o`, `-rtr`, `-rt`, `-depmap` and `--profile`.

A package's own tests, with its dependencies resolved and their capability
ceilings applied, are run by the manifest tool, which resolves the
dependencies, writes the depmap sidecar, and then hands discovery to the
driver:

```text
resid-manifest test <resid.toml> <driver-binary>
```

Not implemented, from earlier drafts: `--update-snapshots`, `--parallel`,
`--sequential`, `--max-cases`, `--max-shrinks`, and `--format junit` (the
runtime knows only `pretty`, `tap` and `json`).

Because a `test` block is its own entry point, a test *file* is its own
process. The tree run therefore aggregates **per file**, and its tally
counts files, not individual assertions:

```text
$ residc test --root src
test: 3 test file/s under src
src/math_test.resid

math_test
  ✓ add: identity (0ms)

Failures: 0 | Passed: 1 | Duration: 0ms
src/net/http_test.resid
...
---
2 file/s passed, 1 failed, 0 did not compile
```

Getting one combined assertion count and one combined duration across files
would require compiling all the files as a single program with one generated
entry point — a multi-root compilation, not yet built. The per-file summary
lines above are each that file's own runner output, passed through.

### 7.2 Exit Codes — implemented

| Code | Meaning |
|---|---|
| 0 | every test passed |
| 1 | a test ran and failed |
| 2 | a file did not compile, or the invocation was malformed |
| 3 | internal error — not produced; reserved |
| 124 | timeout — not produced; no per-test timeout exists |

A file that does not compile exits **2**, not 1, so a broken file is never
mistaken for a failing test. In a tree run the compile error dominates: if
any file failed to compile the run exits 2 even if others failed assertions.
This was a real defect before it was specified: a compile error used to exit
1, which made "the code is broken" indistinguishable from "a test failed".

A non-test compile keeps the checker's own status, unchanged.

### 7.3 Output Formats — implemented

**pretty** (default):

```text
math_test
  ✓ add: identity (0ms)
  ✗ add: zeroes (0ms)
    expectation failed: toEqual
        actual:   4
        expected: 5

Failures: 1 | Passed: 1 | Duration: 0ms
```

**tap** and **json** are also implemented, selected by `--format` or
`RESID_TEST_FORMAT`. See §7.1 for the tree-run shape.

## 8. Capabilities

A test is an entry point, so authority enters a test exactly as it enters
`main` (§1016 of the normative spec): a test block declares its own
`@requires`, and it may use nothing beyond its enclosing program's or
sandbox's ceiling. There is no per-test sandbox (§5.2).

```resid
@requires(environment)
test "reads the environment" {
    expect(environment.get("RESID_NO_SUCH_VARIABLE")).toEqual("");
}
```

Enforced by the same `E0219` as any other function; a test block that uses an
ungranted capability is rejected by name, e.g. `restest0`.

---

## 9. Summary

Implemented: inline `test` blocks, the `*_test.resid` convention, explicit
registration, the matcher set, compile-time discovery and entry-point
generation, per-file and whole-tree runs, filtering, three output formats, and
the exit-code contract.

Not implemented: property-based testing, snapshot testing, custom matchers,
parallel execution, per-test sandboxing and timeouts, per-test result values,
rich structural diffs, compile-time filtering, and the extra CLI flags and
output formats listed in §7.1.

Earlier drafts of this file specified a `test_module`/`register` block form,
`Fn(A, B) -> R` closure types, `#[test]` attributes, a two-argument
`toSatisfy`, and an `Int` form of `toBeCloseTo`. None of those is Resid; §0
gives the real syntax and §2.1 the real signatures.
