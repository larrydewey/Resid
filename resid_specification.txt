==================================================
RESID LANGUAGE DESIGN DOCUMENT
Version 3.6 — Production Ready
==================================================


LANGUAGE DESIGN CONTEXT
==================================================

Resid is an eager compile-time programming language.
The compiler’s primary obligation is maximal authorized
reduction of first-class knowledge.

Runtime behavior consists solely of the residual computation
that remains after all provable reductions have been performed.

The name Resid denotes this residual core.

The pronunciation /ˈrɛz.ɪd/ (REZ-id) or /ˈriː.zɪd/ (REE-zid) is the correct and standard pronunciation for the name.

Core statement:

    Compilation is maximal authorized reduction
    of first-class knowledge.


==================================================
FUNDAMENTAL LAWS
==================================================

  1. Everything begins as compile-time reducible.
  2. The compiler must reduce all provable computation.
  3. Unknown information must be explicitly introduced.
  4. Residual computation enters through rt.
  5. Compile-time computation cannot depend on unresolved
     residual information.
  6. The compiler preserves knowledge whenever possible.
  7. Residual dependencies should be minimized.
  8. Authorized external knowledge enters through providers.
  9. Knowledge acquisition is an effect.
 10. Effects determine reducibility.
 11. External information has provenance.
 12. Runtime uncertainty is explicit.
 13. Knowledge is first-class.
 14. Authority is never ambient and may only be attenuated,
      never amplified, across trust boundaries.


==================================================
1. KNOWLEDGE IS FIRST-CLASS
==================================================

Knowledge may be represented, transformed, reduced,
composed, serialized, transmitted, and inspected.

Knowledge includes values, types, constraints, proofs,
behaviors, capabilities, provider results, residual
values, and effects.


==================================================
2. EXECUTION MODEL
==================================================

A program is progressively reduced until only irreducible
computations remain. Compilation is knowledge reduction.


==================================================
3. INTERNAL REPRESENTATION — KNOWLEDGE GRAPH
==================================================

Programs are represented as a knowledge graph (enriched
expression DAG). The graph is the compiler's sole
representation between parsing and lowering: name
resolution, type checking, capability checking, reduction
and lowering all read and extend the graph, and no phase
re-reads source text. The graph is observable: it is
emitted as an artifact (§33, §34) and is what debuggers
and tools walk (§37).

3.1  Nodes

Each node has:

  id            NodeId, unique within the artifact and
                deterministic (§3.5)
  kind          what the node computes (literal, reference,
                binding, call, operator, cast, if, match,
                loop, provider call, spawn, function, ...)
  type          its resolved type
  knowledge     its knowledge state (§3.2)
  value         the value, when knowledge is KNOWN
  deps          ordered operand edges
  effects       the effects it may perform
  capabilities  the capabilities it requires
  provenance    where it came from (source span, provider
                result, or a derivation, §3.3)
  doc           attached doc comments, if any

Pure nodes with equal kind, type and operands may be
shared (hash-consed). Nodes with effects are never
shared: each occurrence is its own node.

3.2  Knowledge States

  KNOWN     value fully determined at compile time
  EFFECT    performs an effect; its order is fixed
  RESIDUAL  depends on runtime values; it is lowered
  INVALID   carries a diagnostic; the program is rejected

A node is INVALID if it or any dep is INVALID. Otherwise
it is EFFECT if it performs an effect, KNOWN if it is
pure and reduction determined its value, and RESIDUAL
otherwise. Every RESIDUAL or EFFECT node records why it
was not reduced (§3.4).

3.2a  Facts (Partial Knowledge)

A RESIDUAL or EFFECT node may carry facts: properties that
hold of its runtime value on every execution. Facts are
knowledge (§1); they are sound, never guessed.

  range(lo, hi)     integer value lies in [lo, hi]
  bits(zero, one)   masks of bits known to be 0 / 1
  nonzero           value is not 0
  length(lo, hi)    Str, Bytes, List, Map or Set length
                    lies in [lo, hi]
  fields            per-field (or per-element) node ids;
                    known fields are KNOWN nodes
  tag(V)            sum value is variant V
  unreachable       node is never evaluated
  path(c)           condition node c holds here (from a
                    dominating if, match arm, loop test
                    or assert)

Facts come from literals, types (an Int(8) is in
[-128, 127]), operators, conversions, branch conditions,
asserts and known fields. Reduction uses them to:

  - discharge checks: overflow, division by zero, index
    and slice bounds, conversion range, Str(N) capacity,
    capability checks (§27);
  - select a match arm or if branch under a RESIDUAL
    scrutinee (tag, range, path);
  - fold a projection of a known field out of a RESIDUAL
    composite;
  - specialize on known fields (§36).

A discharged check is recorded on its node as a
discharged fact naming the check (overflow, division,
bounds) and the operand nodes whose facts were used, so a
debugger can show why a check is absent. When a check
cannot be discharged, it stays, and its node carries a
check fact naming the check and the operands that had no
range.

3.3  Edges

  operand   node → its i-th dep
  def       reference → the binding, parameter or
            function it resolves to
  seq       effect node → the effect that precedes it in
            evaluation order
  derive    result node → the node it replaces, labelled
            with the rule that produced it (§36)
  lowered   node → the code range and runtime location
            emitted for it (§33)

operand, def and seq edges are acyclic, so the graph is
a DAG; recursion appears as a def edge to a function
node, never as a cycle of operand edges.

3.4  Derivation

Reduction (§36) is graph rewriting that preserves
provenance. A rewrite never deletes a node reachable from
a source root. It adds the result node with a derive edge
to the replaced node, labelled with the rule:

  fold, beta, eval, specialize, generalize, dead-arm,
  elide, discharge, provider, behavior, desugar, widen,
  interpolate

Instantiation (§11, §12) adds its own derive edges before
reduction: a copy from its generic (instantiate), an
instance from the one it displaced (replaces), and a
sandbox rebuilt without its generic declarations from the
sandbox it replaces (prune); a sandbox whose members are
unchanged is kept as written.

A node left RESIDUAL or EFFECT carries a reason:

  unknown(dep)     depends on the named RESIDUAL dep
  effect(e)        performs effect e
  capability(c)    requires capability c that is not granted
  annotated        written with rt / @residual
  budget(kind)     a reduction budget ran out (§27)
  loop             re-entered itself with identical arguments
  whistle          specialization was generalized (§36)

Evaluating a fully known call is recorded as a single eval
derivation. Its internal steps are not graph nodes; they
can be replayed because reduction is deterministic (§27).

Invariants:

  - Every node in the residual program (the part that is
    lowered) is a source node or reaches source nodes
    through derive edges.
  - Every source node is KNOWN, INVALID or lowered, or has
    a derive edge from the node that replaced it.

3.5  Identity

Node ids are assigned in source order and then in
reduction order, so the same compiler emits the same
graph for the same program. Each node also has a content
hash over kind, type and the hashes of its operands; the
knowledge cache (§21.4) and cross-build tools key on the
hash, never on the id.


==================================================
4. VALUE MODEL
==================================================

Values are immutable, have no observable identity, and
may be freely copied. Handles are identity-bearing
runtime resources under capability control. Only handles
may represent mutable state.


==================================================
5. MEMORY MODEL
==================================================

Resid does not expose stack, heap, or register allocation.
The compiler decides storage. The implementation may use
any target ISA extensions (AVX-512, NEON, SVE, …) for
optimization; raw intrinsics are not exposed.

The runtime's own memory management (arenas, persist
copies) is not part of the language: a program that calls
it is rejected (E0220). Only the compiler's own source is
built with it (--runtime-internals).

Fixed-capacity value types (§44) carry a statically known
extent, so the compiler may place them inline in the
activation frame; they never require heap allocation.
Storage placement remains an implementation detail — the
program never observes it.


==================================================
6. PRIMITIVE NUMERIC TYPES (FIRST-CLASS)
==================================================

Numeric types are first-class nominal types.

Integer family (distinct types for every width):

  Int(8)   Int(16)   Int(32)   Int(64)
  Int(128) Int(256)  Int(512)

  UInt(8)  UInt(16)  UInt(32)  UInt(64)
  UInt(128) UInt(256) UInt(512)

Aliases (fixed, reproducible):

  Int  = Int(64)
  UInt = UInt(64)

Pointer-sized (target-dependent):

  ISize    // signed, width of a pointer
  USize    // unsigned, width of a pointer

Floating-point family:

  Float(16)  Float(32)  Float(64)  Float(128)

  Float(128) is the widest floating-point type.
  Wider binary floats are not part of the language;
  arbitrary precision is carried by the decimal
  family below.

Alias:

  Float = Float(64)

Arbitrary-precision decimal family:

  Dec(N)    // N significant decimal digits, any N >= 1

Alias:

  Dec = Dec(34)

Each width is a distinct type. There is no subtyping
between any numeric types.


--------------------------------------------------
6.1  Interoperability — Integer Arithmetic
--------------------------------------------------

Mixed-width integer operations are permitted when both
operands are signed or both are unsigned.

Result width: every integer operator — addition,
subtraction, multiplication, division, remainder, and the
bitwise and/or/xor — yields the widest operand width. The
narrower operand is widened (value-preserving) first.

Arithmetic (+ - * / %) is checked (6.5): a result that does
not fit the result type is an error, never a wider type and
never a silently discarded carry. Implementations must not
emit widen-then-narrow sequences that hide a carry.

Shifts:
    The result width is the left operand's width. Shifts
    and bitwise operators are bit operations on the two's-
    complement representation and are not checked: bits
    shifted out are discarded.
    `<<` fills with zeros. `>>` is arithmetic (sign-filling)
    for signed operands and logical for unsigned operands.
    A shift count that is negative or >= the bit width
    yields 0, except that `>>` of a negative signed value
    yields -1 (counts never wrap modulo the width).

Examples:

  Int(8)   + Int(8)   -> Int(8)    // checked; traps on overflow
  UInt(16) + UInt(8)  -> UInt(16)  // widest operand
  Int(256) * Int(256) -> Int(256)  // checked; traps on overflow
  Int(32)  << 4       -> Int(32)
  Int(-8)  >> 1       -> -4        // arithmetic shift

Headroom for a wide answer must be requested explicitly,
by converting one operand up before the operation:

  Int(512) p = (Int(512))a * b;    // a, b : Int(256)

ISize / USize participate with their actual target width.

Signed and unsigned operands may never be mixed in a
single arithmetic operation; an explicit conversion is
required. Unsigned operands use unsigned comparison,
division and remainder.


--------------------------------------------------
6.1a  Integer Literal Typing
--------------------------------------------------

An integer literal takes its type from its context:

  - As an operand of a binary operator whose other operand
    has a concrete integer type, it adopts that type.
  - When it is the whole expression of a binding
    initializer, argument, return value or field, it
    adopts the declared type of that position.
  - Otherwise (for example `1000000 * 1000000`, where both
    operands are literals) it has the smallest signed
    width from {64,128,256,512} that its magnitude fits;
    magnitudes within 64 bits yield plain Int(64).

A literal that does not fit its adopted type is a
compile-time error at every width and in every base
(decimal, 0x, 0b, 0o), also under `rt` (which keeps the
value from the reducer, not from the check), as a list
element, and as the operand of a cast to an integer type;
it never wraps. Only a literal under a unary minus may
reach the negative bound (-2^(N-1)). Arithmetic on literals
is checked at the literals' type like any other (§6.5):
`9223372036854775807 + 1` traps; a value the reducer folds
at a wider type and that does not fit the type it flows
into is a checked conversion that aborts, never a
truncation. Literal adoption does
not reach through `if` / `match` arms: arms must agree in
type (§18), so write `i128(0)` in an arm that must match an
Int(128) arm.


--------------------------------------------------
6.2  Interoperability — Floating-Point
--------------------------------------------------

Integer + floating-point:

  The integer operand is converted to the floating-point
  type of the other operand; the result is that floating-
  point type.

  Int(32) + Float(64)  →  Float(64)

Floating-point + floating-point:

  The result is the wider of the two floating-point types
  (using the order 16 < 32 < 64 < 128).


--------------------------------------------------
6.3  Comparisons
--------------------------------------------------

Relational and equality operators follow the same
widening rules as arithmetic, except that a signed/
unsigned mix is always a hard error.

The result of a comparison is Bool.


--------------------------------------------------
6.4  Assignment and Narrowing
--------------------------------------------------

Narrowing conversions are never implicit.

  UInt(16) x = some_u32;     // hard error
  UInt(16) x = u16(some_u32); // ok (explicit, checked)

Narrowing assignments always require an explicit
conversion. Value-preserving widening is permitted
implicitly at bindings, returns and fields: same
signedness and no narrower, or unsigned into a strictly
wider signed type. Signed into unsigned is never implicit.
Integer literal adoption (6.1a) applies as specified there.

Explicit conversions — the helpers of 6.7 and the cast
(Type)expr — are checked: a value that the target type
cannot represent (too large, too small, negative into
unsigned, or a NaN / out-of-range float into an integer)
is a runtime error. Bit-level truncation is requested
explicitly with the wrapping conversions of 6.7.

Argument expressions must match the parameter's declared
type exactly, after literal adoption. Computed argument
expressions are never implicitly widened or narrowed to
fit a parameter.

Implementations must never emit widen-then-narrow code
around an assignment: if a computed value does not fit
its target type, the program fails, never truncates
silently.


--------------------------------------------------
6.5  Checked Arithmetic
--------------------------------------------------

After operands have been brought to the common result
type, + - * / % are checked at every width (8 through
512 bits). Overflow of the result type, division or
remainder by zero, and signed MIN / -1 are runtime errors
that abort the process (a region's failure inside spawn,
§19). MIN % -1 is 0.

An out-of-range integer literal is a compile-time error
(6.1a). Any other overflow is detected when the operation
executes. Compile-time reduction never folds an
overflowing operation: it leaves it residual, so reduced
and unreduced programs fail identically (§36).

Wrapping and saturating variants (wrapping_add,
saturating_mul, …) are supplied by the standard library
for every width.


--------------------------------------------------
6.6a Decimals — Dec(N) Semantics
--------------------------------------------------

Dec(N) holds an exact decimal value with N
significant decimal digits:

  sign        + or -
  digits      exactly N significant decimal digits
  exponent    i32, range [-1_000_000, +1_000_000]

Dec(N) values have no NaN and no Inf. Division by
zero, exponent-range overflow, and non-integer
Dec-to-Int conversion are errors: compile-time when
provable, residual errors when forced at runtime.

Rounding:

  When a result must be narrowed to N significant
  digits it is rounded half away from zero:

    0.255    ->  0.26     // to 2 digits
    -0.255   ->  -0.26    // to 2 digits

  Additive and multiplicative arithmetic computes
  the exact decimal result, then rounds once. Division
  computes to N + 2 guard digits, then rounds once.

Interoperability:

  Dec(N) op Dec(M)  ->  Dec(max(N, M))

  Mixing Dec with Int, UInt, or Float in either
  direction is a hard error. Conversion is always
  explicit via dN / iN / fN helpers.

  Dec-to-Int conversion requires the value to be
  integral; a fractional part is an error.

Literals:

  1.5m   123.456m   5m

  Decimal literals carry their digits verbatim; they
  never round-trip through binary. The default type
  is Dec(34). Scientific notation is not part of v1
  decimal literals.

Display:

  Dec values print in fixed notation with all N
  significant digits; trailing zeros are preserved.

    Dec(4) 1.5   ->   "1.500"

  The f-string flag `trim` drops them:

    f"{x:trim}"   ->   "1.5"

  A Dec's precision is its type, so a `precision`
  applies to Float only (§14.4).


--------------------------------------------------
6.6  Behaviors
--------------------------------------------------

Eq, Ord, Hash and Bounded are supplied for the entire
numeric family by generic behavior definitions. The
compiler instantiates them for every concrete width. Users
never need to declare per-width instances. Bounded's verbs
take no argument, so a width's bounds are read as `x.min()`
and `x.max()`.


--------------------------------------------------
6.7  Conversion Helpers
--------------------------------------------------

  i8 i16 i32 i64 i128 i256 i512
  u8 u16 u32 u64 u128 u256 u512
  f16 f32 f64 f128
  dN            // any N >= 1: exact conversion to Dec(N),
                // from Int (exact) or Str (exact decimal parse)
  isize usize

Plus the ordinary C-style cast (Type)expr. Both are checked
(6.4).

abs(x), min(a, b), max(a, b) and clamp(x, lo, hi) take
arguments of one numeric type and return that type; abs
of the most negative integer traps like any overflow.

sqrt(x) takes a Float (or a Float vector, lanewise, §46)
and returns its correctly rounded IEEE 754 square root (sqrt
of a negative number is NaN, which prints as `nan` whatever
its sign bit).

These names (abs, min, max, clamp, sqrt, and splat, lanes
and select of §46) are builtins only where the program
declares no function of that name: a user function of the
same name is called instead, everywhere in the program.

Wrapping conversions keep the low bits of the two's-
complement representation, for bit-level code:

  wrapping_i8 … wrapping_i512
  wrapping_u8 … wrapping_u512

  wrapping_u8(300)    // 44
  wrapping_u64(-1)    // 18446744073709551615

6.8  Constant-Time Helpers
--------------------------------------------------

Code that handles secrets (keys, nonces, shared secrets) must
not let a secret steer a branch, a conditional move or a memory
address. Three builtins support writing and checking such code;
each returns its argument unchanged:

  ct_secret(x)    // any integer: x, marked secret for checking
  ct_public(x)    // any integer: x, deliberately made public
  ct_hide(x)      // an integer of at most 64 bits: x, opaque
                  // to the optimizer

ct_secret and ct_public are valgrind client requests
(MAKE_MEM_UNDEFINED, MAKE_MEM_DEFINED) on the value's bytes:
under memcheck a branch, select or address computed from a
ct_secret value is reported, and ct_public marks a
declassification point (a verdict such as "the tag matched", a
signature that is published anyway). Outside valgrind both are
a few instructions and have no effect.

ct_hide passes x through an empty inline assembly statement,
so the optimizer cannot see its value: a mask built from it
(0 - ct_hide(bit)) stays a mask and is not turned back into a
branch or a conditional move.

None of the three is reduced at compile time; a call on known
arguments stays in the residual program. tests/ct runs the
library's secret-handling code under memcheck this way.


==================================================
7. BINDINGS AND IDENTITY
==================================================

  Type x = expression;

Bindings are immutable. Shadowing is forbidden everywhere.
There are no assignment operators.

Names have a fixed case (E0222). Values, functions,
parameters, fields and behavior verbs start with a
lowercase letter or `_`; types, behaviors and sum variants
start with an uppercase letter. A single uppercase letter
(T, K, V, N) is a type parameter (§12) and never names a
declared type, so a value can never collide with a type and
`(T)x` is always a cast.

Discard:

  _ = expression;


==================================================
8. FUNCTIONS
==================================================

  Ret name(Type1 p1, Type2 p2 = default) {
      body
  }

Defaults must be pure compile-time expressions.
Named arguments are permitted:

  draw(x = 10, y = 20, color = red);

Entry point: Int main().

Generic functions. A function whose signature names a type
parameter (§12) is generic:

  T first(List(T) xs) { return xs[0]; }
  Int(N) clamp_pos(Int(N) x) { return if (x < 0) { 0 } else { x }; }

A call fixes each parameter from its arguments, else from
the expected type of the call, else from the one instance
(or enclosing need) that fits one of its needs, which also
fixes a parameter named only in @needs (E0227 when none
does), and calls a copy of the function made for those types.
Copies are made at compile time, before reduction, so the
reducer sees only concrete functions; every copy is
recorded in the knowledge graph. A generic function that
calls itself at ever larger types (polymorphic recursion)
is rejected (E0228).

A generic function states the behaviors it relies on:

  @needs(Ord(T), Show(T))
  Str top(List(T) xs) { return f"{sort(xs)[0]}"; }

Inside its body, sorting, displaying, comparing (==, <) or
calling a behavior's verb on a T requires the matching
need (E0226); every call checks that each need is met for
its types (an instance, or a built-in one). A need over the
function's type parameters is also met, without listing it,
by an instance that covers it for every choice of them whose
own needs are met there: with `Encode(Int, F) = enc_int` and
enc_int needing Encoder(F), a body with @needs(Encoder(F))
may encode an Int to any F. Each copy then uses that
instance. When the arguments leave a parameter open, the
callee's needs fix it before a lambda argument is typed
(`fold(xs, 0, lambda(a, x) { a + x })`). A call may
override a need: `top(xs, using = Reverse(Ord(Int)))` or
`top(tasks, using = by_deadline)`.


==================================================
9. RESIDUAL COMPUTATION
==================================================

  Type x = rt expression;
  @residual Type y = expression;

Residual values are first-class knowledge.
Top-level residual force or unwrap failure aborts the
process. Inside a concurrent region, failure is delivered
as Result.

  known(x);        // compile-time hard error if residual
  rt_known(x);     // residual check


==================================================
10. EFFECTS
==================================================

Effects are first-class. They do not appear in signatures;
capabilities (@requires) are the sole authorization surface.


==================================================
11. BEHAVIORS
==================================================

Behaviors are ordinary compile-time knowledge: a behavior
names what can be done with a type, and an instance states
how, for one type, from outside the type.

A behavior declares one or more functions as prototypes;
each prototype is a verb:

  behavior Area(T) {
      Float area(T shape);
  }
  behavior Shape(T) {
      Float surface(T s);
      Float perimeter(T s);
  }
  behavior Convert(A, B) {
      B convert(A x);
  }

An instance gives the function (or, for several verbs, a
record of functions, one per verb, comma-separated):

  Area(Circle) = circle_area;
  Shape(Square) = { .surface = sq_area, .perimeter = sq_perimeter };
  Convert(Celsius, Kelvin) = c_to_k;
  Show(Pair(T)) = show_pair;      // every T; show_pair has @needs(Show(T))

A behavior of one function takes the function directly; one
of several takes a record naming every verb. An instance
that names some but not all of a multi-verb behavior is an
error, and so is one for a verb the behavior does not
declare. Ord is now such a behavior, so an ordering for a
user type gives all three:

  Ord(Task) = { .compare = by_priority, .least = lo_prio, .greatest = hi_prio };

The instance's functions must have the prototypes'
signatures for its types. A verb call picks the instance
for its argument types (and the expected type, for a type
that appears only in the result) at compile time and calls
its function: `area(c)` is `circle_area(c)`. A behavior type
fixed by neither comes from the one enclosing @needs, else
the one instance, that fits the known types: with
Container(Stack(T), T), `count(s)` on a Stack(Str) has E =
Str (E0227 when none or several fit). `using = f`,
`using = B(T)` or `using = Reverse(..)` overrides the choice
at one call.

Method syntax. A verb may also be called on its receiver:
`c.area()` is `area(c)`, and `s.compare(t)` is
`compare(s, t)`. The receiver is the verb's first
parameter, so the call is the same one. A verb that takes
no parameter takes its types from the receiver and is not
passed one: `x.min()` passes no argument, and the types come
from x, from the expected type in a value position, or from
the enclosing @needs.

  Int(8) a = 100;
  Int(8) lo = a.min();     // lo = -128, from Bounded(Int(8))

A verb name belongs to one behavior. Where two behaviors
declare it, the one declared last owns the name, and the
prelude is appended last of all: a behavior of the program's
own that redeclares a prelude verb's name is not reachable
by that name. The core behaviors are named so that they do not
collide: Ord takes least and greatest where Bounded takes
min and max, and the numeric builtins keep min, max and
clamp for two arguments.

A name is a verb or a function, never both (E0231). Were
both possible, `show(m)` would not say which one it meant. A
function may therefore not reuse a verb's name, which takes
`min`, `max`, `least`, `greatest`, `show`, `hash`, `eq`,
`compare` and `serialize` out of circulation program-wide.
Overriding a behavior is done through an instance or `using`,
never by defining a function of a verb's name.

There are no default bodies: a type gets an instance only
from a declaration, which may name a generic function
(`Eq(Task) = eq_from_ord;` with eq_from_ord needing
Ord(T)), so a derivation is explicit and recorded.

Coherence. A program has at most one instance per behavior
and type. Two instances at the same level whose types
overlap (Show(Pair(T)) and Show(Pair(Int))) are an error
(E0225): there is no specialization. Levels rank the
application over a library over the prelude; a higher
level's instance replaces a lower one for its type
program-wide (recorded in the graph). A library may declare
an instance only of its own behaviors or types (E0224); the
application may declare any.

Which widths an instance carries. An instance's head may
be generic in a width (Encode(Int(N), F)), and the needs in
its body decide which widths it carries: a need that holds
for some widths and not others (a need over a type the
width names, with instances for the widths that have it)
excludes the rest, so one declaration covers exactly the
widths its body serves and a call with another width is
E0226, naming the width and the need left unmet. The
coherence rule above reads the same way: two instances
overlap only where both apply, so a generic instance and a
specific one for one of its widths are not an E0225. A
need left open by the substitution is not decided here: the
copy made for the call resolves it.

Authority. An instance's function is called where the
behavior is used. A generic function's authority is its
own @requires plus what its instances need, checked at each
concrete call: the caller of `label(task)` holds what
Show(Task)'s function uses.

Resid has no trait or interface system (§38). A type never
declares what it implements; behaviors are not methods on a
type; no value of an unknown type dispatches at run time
(every instance is resolved at compile time); behaviors do
not form hierarchies (a function lists each need); and a
behavior contains no types of its own.

Core behaviors. Eq, Ord, Hash, Show, Serialize, Bounded
and Allocator are ordinary behaviors declared in the
prelude (§32), with instances for the built-in types:

  behavior Eq(T) { Bool eq(T a, T b); }
  behavior Ord(T) {
      Int compare(T a, T b);
      T least(T a, T b);
      T greatest(T a, T b);
  }
  behavior Bounded(T) { T min(); T max(); }
  behavior Hash(T) { Int hash(T x); }
  behavior Show(T) { Str show(T x); }
  behavior Serialize(T) { Str serialize(T x); }
  behavior Allocator(T) { T allocate(); }

  Ord(Int) = ... ;
  sort(values, using = Reverse(Ord(Int)));

sort(xs) on numeric or Str elements uses their built-in
order; on other types, the element type's Ord instance.
== and != on a type with an Eq instance, and < <= > >= on a
type with an Ord instance, call it.

Bounded gives a type's least and greatest value, and takes
no parameter, so it reads as a method on the receiver:
`x.min()`, `x.max()`, or `min(x)`. It is declared for Bool,
Int(N) and UInt(N), covering every width:

  Bounded(Bool)   // false, true
  Bounded(Int(N)) // -2^(N-1), 2^(N-1)-1
  Bounded(UInt(N))// 0, 2^N-1

Since Bounded's verbs take no argument, it is the one
behavior read purely as a method: its min/max are the
two's complement bounds, while Ord's `a.least(b)` is the
lesser of two values and is reached by name.

Lists: xs.contains(v) (integer, Float or Str elements),
xs.reverse(), xs.sum() (List(Int) or List(Float)). A
function of the same name taking the list as its first
parameter takes precedence.

min, max and clamp are also builtins: min(a, b) and max(a,
b) are the builtins, with an integer literal argument
adopting the type of the others (§6.1a). They want numbers,
so a `T` of your own uses Ord's `a.least(b)` instead. A
bare `max()` with no argument is Bounded's, but with no
receiver to fix the type it takes the expected type, so
give it one: `Int(8) hi = max();`.

Numeric Eq / Ord / Hash are supplied generically for
the whole family (see §6.6).

Show(T) = f, with f : (T) -> Str, is how a T is written:
an f-string hole of type T calls f, including a record
field of type T. Without an instance, numbers, Bool, Str,
Dec, lists and records have built-in text (see §14);
numbers, Bool and Str cannot take a Show instance.


==================================================
12. TYPES
==================================================

Product:  type Point = { x: Int, y: Int };
Sum:      type Option(T) = Some(T) | None;
          type Shape = Circle(Int) | Rect(Int, Int) | Empty;
Generic:  type Pair(T) = { T a; T b; };
          type Entry(K, V) = { K key; V value; Int hits; };

A sum type is one or more variants separated by `|`. A variant
carries zero or more payload types: `Empty` carries none,
`Circle(Int)` carries one, and `Rect(Int, Int)` carries two. Each
payload position is an ordinary type, so it may be concrete or a
type parameter, and the positions are independent — `Cell(T, Int)`
and `Cell(List(T), T)` are both well-formed. A payload list is not
a tuple type; it is the variant's own ordered set of carried
values, so the n positions of `Rect(Int, Int)` are read and
matched by position and are unrelated to each other's types.

A variant with a payload is constructed by calling it with one
argument per payload position, in order: `Rect(3, 4)`, and a
variant with no payload is written bare: `Empty`. Supplying the
wrong number of arguments is an arity error.

A pattern for a variant binds one name per payload position, or
none at all: `Rect(w, h)` or `Empty`. A partial list is an error,
so a pattern always takes the whole payload; to ignore a value,
bind it to `_`. The rules are in §13 and the grammar in §31.

Type parameters are single uppercase letters (§7). In a
width position (`Int(N)`, `UInt(N)`, `Float(N)`) a
parameter ranges over widths. An integer width is a
value too: read in a value position it denotes the width,
so `Int(N) f() { ... N ... }` reads N as an `Int(N)` that
reduction fixes to a literal in every copy. Only `Int` and
`UInt` carry such a value. A float or decimal width, a
capacity (`Str(N)`, `Bytes(N)`), and a parameter that
stands for a type have no value and stay an error there. A
generic record's literal
takes its type arguments from the expected type or from its
field values (`Pair {.a = 1, .b = 2}` is a Pair(Int)); each
generic record used at concrete types is laid out per type.
An unknown type name of more than one letter is an error.
Constraint: type Positive = Int[value > 0];
            type Positive = Int where value > 0;

Residual types are permitted. Edge-case rules R1–R5 remain
in force.

Numeric types are first-class (see §6). Fixed-capacity
value types — Str(N), Bytes(N), List(T, N) — are core
types whose storage is statically bounded (see §44).


==================================================
13. PATTERN MATCHING AND DESTRUCTURING
==================================================

  match expression {
      Some(x) => expression,
      None    => expression
  }

A variant pattern takes one binding per payload position, in
order, or none when the variant has no payload:

  match shape {
      Circle(r)     => ...,
      Rect(w, h)    => ...,
      Small         => ...,
      Tagged(k, v)  => ...
  }

A binding list is all-or-nothing: `Rect(w)` against a two-payload
`Rect` is an error, as is `Some()` or a bare `Some`. To discard a
value, bind it to `_` (`Rect(_, h)`), which is not a binding and
needs no name. The bindings of one arm shadow nothing and are
visible only in that arm's body.

Irrefutable destructuring:

  Point { x, y } = p;
  Some(v) = opt;          // hard error if refutable

if-let / while-let:

  if (Some(x) = opt) { ... }
  while (Some(x) = it.next()) { ... }


==================================================
14. LITERALS AND COMPOSITES
==================================================

  42  0x2A  3.14  1.5m  'a'  "hello"  true  false
  [1, 2, 3]   {"a": 1}   Point { x = 1, y = 2 }

  f"hello {name}"
  f"{price:trim}"
  f"{total:12, group, left}"
  r"C:\path\file"
  b"bytes"

An f-string hole takes a value of any type: numbers and
Bool as decimal text (Float round-trips), Str as is, Dec at
its precision, lists and records structurally, or through a Show(T)
instance (§11). `f"{x}"` is how a value becomes a Str; there
are no per-type conversion functions.

`{{` and `}}` are a literal brace. A single `}` in an
f-string's text is a parse error: write `}}`.

Escapes in "...", f"...", b"..." and '.' are \n \t \r \0
\\ \" \' and \xHH (two hex digits). Any other escape is a
parse error. Text is ASCII through \x7f; a byte above that
belongs in a byte string. A Str ends at NUL, so \0 and \x00
are refused in text (a byte string and a character take
them). A heap Bytes also ends at its first zero byte, so a
byte string with \0 or \x00 is refused unless it is a
Bytes(N) (§44), which holds exactly N bytes. r"..." has no
escapes.

14.1  A hole's format spec

A hole may carry a spec after `:`. The spec is a
comma-separated list of flags, in any order:

  f"a {n:8} b {s:width 8, left} c {f:precision 2}"

Every flag names one thing. There is no positional
mini-language to remember beyond one shorthand: a bare
integer is the width. An empty spec is the value's own
display, so `f"{x}"` and `f"{x:}"` agree.

  width N        minimum field width, in codepoints
  8              the same, as a shorthand
  left           align to the left edge
  right          align to the right edge
  center         center the text
  fill 'x'       the pad character; `fill 0` also works
  zero           pad with '0', after any sign
  plus           show + for a non-negative value
  space          show a blank for a non-negative value
  minus          show - only (the default)
  hex oct bin    write an integer in that radix
  upper lower    the case of the letters (hex digits,
                 or text)
  group          a ',' every three digits (decimal only)
  precision N    digits after the point, for a Float
  .N             the same, as a shorthand
  auto           the value's own text (the default)
  decimal        fixed point
  scientific     one digit before the point, an exponent
  percent        the value times 100, then `%`
  trim           drop a Dec's trailing zeros

14.2  What the defaults are

Width pads to the width and never truncates. Alignment
defaults to `right` for a number and `left` for
everything else, so a spec says only what differs. The
pad character defaults to a blank, except that `zero`
means '0' after a sign: `f"{-42:zero, width 6}"` is
`-00042`, never `0-042` or `00-042`.

Without a style a Float prints the shortest text that
reads back as the same value, and a Dec prints all N of
its digits. `precision` changes the digits; the styles
change the shape.

14.3  The order the flags apply

A style or a radix writes the value out; `group` then
counts its decimal digits; `upper`/`lower` moves the
letters; `plus`/`space` puts the sign in; the width pads
last, so the sign counts toward it.

14.4  A spec is checked against its type

Every flag names something only some values have, so a
flag a type cannot mean is E0413 rather than silently
ignored. `hex` needs an integer, `precision` a Float,
`trim` a Dec, `group` and the sign flags a number. A
combination that cannot be one value is refused too:
`group` counts decimal digits, so it does not go with
`hex`; a Dec's precision is its type, so `trim` and
`precision` do not go together; a Float(128) carries
more digits than a double can round to, so no style and
no precision apply to it.

An unknown flag, a repeated one, and a missing argument
are parse errors, and the diagnostic names the flags
that are accepted.

14.5  Reduction

A spec never changes how a value is computed, only how
its text is written, so it is applied as text operations
after the value is known. When the hole's value reduces,
the spec is applied at compile time too, by the same
code the runtime would run, and the hole folds to its
text. `f"{n:group}"` with a known `n` is a literal.

Literals default to Int / Float / Dec (for m-suffix
decimals); integer literals follow 6.1a. There is no null
literal: absence is Option's None. Width is otherwise
changed only by an explicit conversion.

A literal may adopt a fixed-capacity expected type from an
annotated binding when its extent fits the declared
capacity; an oversized literal is a compile-time error and
is never silently truncated (§44.1).

==================================================
17. FIELD AND INDEX ACCESS
==================================================

  p.x   xs[i]   m[k]

Indexing is bounds-checked: an out-of-range index aborts the
program with the offending index and length (resid_index_abort);
it never reads out of bounds silently.

  xs.with(i, x)

`xs.with(i, x)` is the list xs with element i replaced by x.
xs itself is unchanged: values are immutable (§4), so every
other name for xs still sees the old elements. The index is
checked as for `xs[i]`: an index outside 0..xs.len() aborts
with the index and the length (resid_index_abort). x has the
element type of xs; the result has the type of xs. The same
verb replaces an element of a List(T, N) (§44.3) and a lane
of a vector (§46.1).

How the result is stored is the compiler's choice (§5): when
xs is never read again (its one consuming use is this update,
as for a Map's `insert`), the element may be replaced where
it is; otherwise the result is a new list sharing what it can
with xs. Neither is observable.

Access to a fixed-capacity value is bounds-checked against its
declared capacity and aborts identically on an out-of-range
index (§44.3).

  xs.len()   s.len()   b.len()   m.len()

`.len()` is defined on lists, text, bytes, maps and sets, and
nowhere else (a compile-time error). On a Str or Str(N) it is
the codepoint count, equal to str_len(s); on Bytes, the byte
count; on a map or set, the entry count. `xs.concat(ys)` joins
two heap lists of one type, and the slice `xs[..hi]` takes a
heap list and an integer bound; neither applies to text, bytes,
fixed-capacity lists or any other value.

Shift counts that are negative or >= the operand's bit width
yield 0, or -1 for `>>` of a negative signed value (§6.1); they
never wrap modulo the width. This holds for every integer width,
including wide Int(N)/UInt(N).

18. CONTROL FLOW
==================================================

Classic C plus:

  for (Type x in xs) { ... }

  if (Some(x) = opt) { ... }
  while (Some(x) = it.next()) { ... }

The arms of an if-expression or match must all have the
same type (numeric aliases such as Int and Int(64) are the

type.


==================================================
19. CONCURRENCY
==================================================

Structured concurrency:

  Result(T, RegionError) r = spawn (cap1, cap2) {
      return value;
  };

Rules:

  - Capabilities listed explicitly; child ≤ parent.
  - Child receives a fresh CapEnv: the spawn body and
    everything it calls may use only the listed
    capabilities (E0214), and the child thread runs in
    its own force-time frame. A closure the body calls
    by the name it is bound to counts as called, so
    what its lambda uses must be listed too; a closure
    reached any other way is bounded by that frame
    when it runs (§21.3).
  - Residual forcing uses only the child’s CapEnv.
  - Returns pure values or residuals.
  - Mutable handles moved; immutable views shareable.
  - Child failure → Err(RegionError) to parent.
  - Nested spawn permitted.
  - Scheduler implementation-defined.
  - Work may run in parallel; completion is structured.


==================================================
20. CAPABILITIES AND SECURITY
==================================================

No ambient authority. Capabilities form a lattice and
travel with effects, handles, and residuals. Revocation
is monotonic within an execution / region.

Authority may only be attenuated across trust boundaries;
it may never be amplified.

Every capability family a function uses must be granted
to it (E0219): by its own @requires, or, when it has
none, by its enclosing sandbox. A function uses what its
provider calls and effectful builtins use, and what each
function it calls, wraps in a closure, or runs as a sort
behavior uses or declares. So authority enters a program
only where `main` (or a `test` block) declares it:

  @requires(args, filesystem(readonly))
  Int main() { ... }

@requires entries take the same modes as sandboxes; a
read-only grant does not cover a write (filesystem write
verbs, process.run, clock.sleep_ns, terminal raw mode,
binding a listener to an address other than loopback).
Families:

  filesystem, environment, args, process   (providers)
  clock                                   (provider)
  network      TCP builtins
  terminal     TTY and raw-mode builtins
  process      also the native debugger builtins
  display      the display builtins (resid_disp_*): the
               connection to a window server, the bytes and
               descriptors on it, a shared mapping, and
               waiting on it; with no modes
  native_<m>   a call into native module m (§47); one
               family per module, with no modes
  declassify   publishing a secret: declassify(s, "reason")
               (§48); with no modes

network(readonly) covers connecting out, listening on
127.0.0.1, accepting, sending and receiving: everything a
program does over connections it opened or accepted.
Exposing a port to other machines (resid_tcp_listen_at, a
bind to any address but loopback) is the one network
write, so it needs the full grant. A server's workers can
then run under network(readonly) while only the code that
binds the public listener holds network.

display has no modes: connecting to a window server, opening
a window, drawing into it and reading from it all act on
what the program itself put on screen, so a program is in it
or out of it (display(readonly) is refused, E0213). A display
descriptor is a socket, so resid_disp_poll waits on one under
display alone; a program that waits on display and TCP
descriptors together needs both families. Nothing outside
this machine's own session is reachable through it: a DISPLAY
naming another host is refused.

Writing to stdout/stderr, reading stdin and OS randomness
are not capabilities.


==================================================
21. SANDBOXING AND LIBRARY ATTENUATION
==================================================

A program may restrict the capabilities available to a
third-party library or any untrusted region of code.

--------------------------------------------------
21.1  Policy Ceiling (Manifest)
--------------------------------------------------

The project manifest supplies the maximum set of
capabilities any dependency may receive:

  [dependencies.http]
  path = "vendor/http"
  capabilities = ["filesystem(readonly)", "network"]

This is a ceiling. Source code may only further restrict;
it may never enlarge the set.

Every entry must be grantable under the manifest's
[capabilities] grant, modes included: a read-only grant
covers only a read-only entry, so `filesystem` is refused
under `filesystem(readonly)`. The ceiling a dependency
writes for one of its own dependencies must be grantable
under the ceiling it was itself given, so authority only
narrows down the dependency tree. A dependency that two
packages declare receives the meet of every ceiling given
to it (per family; read-only when either is), whichever
declaration resolution reaches first, and every pinned key
any declaration names must verify.

--------------------------------------------------
21.2  Source-Level Attenuation
--------------------------------------------------

Capabilities may be narrowed at the import site or with
an explicit sandbox:

  import "http.resid" (get, post)
      @requires(filesystem(readonly));

  sandbox (filesystem(readonly)) {
      // all code and transitive imports herein
      // see only the listed capabilities
  }

An attenuated import compiles the module inside
`sandbox (caps)`. A module already imported without that
bound cannot take it afterwards (E0216): import it
attenuated first. Nested sandboxes meet (only narrow),
and `sandbox ()` grants nothing.

A manifest dependency is compiled inside the ceiling its
consumer's manifest lists (the driver's -depmap lines
"name::root::caps").

--------------------------------------------------
21.3  Enforcement
--------------------------------------------------

  - When a required capability is statically apparent
    and exceeds the sandbox, compilation fails with a
    hard error.
  - When the requirement is dynamic or residual, the
    call remains residual and fails at force time with
    a capability error. Every provider call is checked
    before it runs against the calling thread's sandbox
    frames; a write needs a grant that is not read-only.
  - A closure carries no authority of its own: its body
    runs under the frames where it is called, not where
    it was made. A lambda made where a family is granted
    and called inside a sandbox or spawn that drops the
    family fails at its provider call, as a named
    function's body would (Law 14: authority crosses a
    boundary only attenuated).
  - Transitive dependencies are closed under the same
    sandbox; attenuation applies to the entire closure.
  - A handle may enter a sandbox only when every
    capability it requires is ≤ the sandbox’s set.
    Otherwise the program is rejected at compile time
    or the handle use becomes a residual capability
    error.

--------------------------------------------------
21.4  Knowledge Cache Interaction
--------------------------------------------------

Sandboxed compilation may read the global knowledge
cache. It may write cache entries only when the
capabilities associated with those entries are ≤ the
sandbox’s granted set.

(Implementation status: the self-hosted toolchain has no
knowledge cache, so there is nothing to read or write.)

==================================================
27. RUNTIME OPTIMIZATION AND MINIMIZATION
==================================================

The implementation shall reduce every provable
computation. It shall not retain residual work that can
be discharged under the granted capabilities and the
available knowledge cache.

Residual notes should make remaining residual work
visible so that later compilations, with additional
knowledge, can eliminate it.

The compiler’s primary performance obligation is
therefore:

  1. Maximize compile-time reduction.
  2. Minimize the residual surface that reaches runtime.
  3. Lower only what remains to efficient native code
     (LLVM).

The reduction outcome is deterministic: budgets count
evaluation steps, calls and the size of the values the
evaluator builds, never time or the compiler's native
memory, so every implementation of the compiler reduces a
given program the same way. Program meaning never depends
on a budget: reduced and unreduced programs have identical
observable behavior, and a budget only decides how much
work is left residual. Every budget that leaves work
residual is reported as a compiler note ("note: reduce:
...").

The budgets:

  fuel     evaluation steps over the whole program
           (default 16,000,000; `--reduce-budget N`,
           `--reduce-budget unbounded`, or `[reduce]
           budget` in resid.toml).
  steps    one top-level call's attempt. The first
           attempt has 65,536 steps; a call that runs
           out is tried again with twice as many, up to
           an eighth of the fuel left, so cheap calls
           cost nothing and an expensive one wastes at
           most what it finally needs.
  memory   a meter of what one attempt holds: each step,
           each call that is not a tail call, and the
           length of each value built and each encoded
           value read. It is a quarter of the compiler's
           memory budget (RESID_MEM_LIMIT, default
           4096 MB; half under `unbounded`). A tail loop's
           meter returns to its start each iteration.
  depth    non-tail nesting, 20,000 calls (none under
           `unbounded`).
  specs    specialization attempts: 400 per program and
           8 per function (more does not make the code
           faster, measured on the compiler itself and
           the benchmark suite).

`@reduce(steps = N)` (or `steps = unbounded`) on a
function gives each of its top-level calls N steps of its
own, outside the fuel. `@fold` on a function makes every
call of it reduce at compile time, with no step limit: a
call with an argument that is not known, or one that does
not reduce, is error E0903 (calls inside another `@fold`
function are exempt; they reduce where that function's
calls do). A malformed `@reduce` is E0904.

What the compiler has may still run out first. The
evaluator recurses on the compiler's stack; past its end
the build fails with E0902 rather than leaving the call
residual (raise RESID_STACK_MB), since how much stack
there is is not a budget. Past the memory budget the
compiler aborts.

Release builds may omit diagnostic metadata from residual
thunks. Capability checks may be elided when the required
set is statically known to be present for the relevant
lifetime. Pure prefixes of residual graphs should be
evaluated at compile time whenever possible.


==================================================
28. PACKAGES, SIGNATURES, AND INTEGRITY
==================================================

A package is a directory containing resid.toml, source
files (*.resid), and optional knowledge-cache /
residual-notes artifacts.

Distribution units are content-addressed archives.

--------------------------------------------------
28.1  Package Signature
--------------------------------------------------

A package archive holds every .resid, .toml and .ll file of
the package (the last are native module artifacts, §47),
sorted by path, so its SHA-256 content hash covers the
source tree, the code it links, and the manifest (name,
version, dependencies, declared capabilities) and
resid.lock (dependency hashes).

A published package carries an Ed25519 signature over the
hex content hash (<name>-<version>.resid-sig beside the
archive), and a signing registry also signs its index of
name, version and content hash. A path dependency may be
signed in place (<name>.resid-sig over the hash of its
packed sources).

A registry is named either by a local directory or by an
http:// base URL, and a manifest that names both is an
error rather than a precedence rule: which one a build
read from should be written down, not inferred.

A remote registry is untrusted input exactly as a local
one. The transport widens nothing -- the content hash, the
archive's own manifest, and the trust decision of 28.2 are
all unchanged by where the bytes came from, and a
completed fetch is never itself a reason to trust
anything. The archive is binary and is carried as bytes,
never as text; a response must declare its length, so
that a registry cannot stream an unbounded amount at a
build. https:// is refused rather than downgraded to
plaintext.

Serving a registry is the same artifact layout read over
HTTP: a listener bound to the loopback interface, GET
and HEAD only, no upload, and a request path that could
name a file outside the registry directory is refused.

--------------------------------------------------
28.1a  Index Operations
--------------------------------------------------

Publishing maintains a registry's signed index. Reading
it, vouching for an entry, withdrawing one, and checking
that it still verifies are separate operations, and every
write re-signs the whole index: the signature covers the
index text, so there is no per-row signature to keep in
step.

Vouching for an entry is not free-form. Where an archive
is already published under that name and version, the
hash offered must be the hash of that archive; a caller
cannot assert a hash that the registry's own contents
contradict. An entry naming a version the registry does
not carry may be vouched for, which is how an index
covering a mirror is built.

Withdrawing an entry that is not there is an error, not
a silent no-op: a publisher who believes they removed
something should be told when they removed nothing.

--------------------------------------------------
28.2  Verification
--------------------------------------------------

Before a package is accepted into a build:

  1. The content hash is recomputed and must match.
  2. The signature must verify against a trusted key
     (project keyring or explicitly pinned keys), or a
     trusted registry's signed index must list the
     content hash.
  3. The archive's manifest must name the requested
     package and version.
  4. All dependency hashes must match the resolved
     artifacts.
  5. Required capabilities must be grantable under the
     current manifest policy, modes included (§21.1).
  6. Each native module artifact must have the SHA-256
     its manifest pins (§35, §47).

Failure of any check rejects the package.

--------------------------------------------------
28.3  Key Management
--------------------------------------------------

Projects maintain a keyring of trusted publisher keys
([signing] keyring, a directory of hex .pub files). Keys
may be pinned per dependency (pubkey). Unsigned packages
are rejected unless the project explicitly allows them
under a development profile ([signing] allow_unsigned =
true). Path dependencies without a pinned key are local
source and are not signature-checked. Secret keys are
written readable by their owner only
(filesystem.write_secret).

A signed index entry and a signature over the archive
are different claims. The first says a publisher wrote
this hash down; the second says a key holder vouched for
these exact bytes. A project that wants the second sets
[signing] require_signatures = true, and a registry's
index then no longer admits a package on its own: a
detached signature under a pinned or keyring key is
required.

require_signatures says nothing about path
dependencies, which 28.3 already exempts as local
source, and it does not weaken allow_unsigned -- it is
the stronger of the two, and a project that set both
gets the stronger one.

--------------------------------------------------
28.4  Chain Validation and Revocation
--------------------------------------------------

A certificate may sign for another only if it says so:
basicConstraints must carry cA TRUE and keyUsage must
allow keyCertSign. A certificate that does not is not
an issuer, whatever its name says it issued. The
check is on the issuer, not on the chain's shape, so a
leaf offered as an intermediate cannot issue.

Certificate signatures are verified for ECDSA P-256,
RSA PKCS#1 v1.5 and RSA-PSS. RSASSA-PSS carries its
own parameters, and they are read rather than assumed:
the hash, the mask generation function's hash and the
salt length must be the ones implemented, because
RFC 4055's defaults are SHA-1 and a signature verified
as SHA-256 that was made as SHA-1 is a different
signature than the one that was made.

Revocation is by certificate revocation list. A CRL is
used only when the certificate's issuer signed it and
it is inside its thisUpdate..nextUpdate window, so a
list that has gone stale certifies nothing. A store
carrying CRLs enforces them: a certificate an issuer's
current CRL lists is refused. A store that also
requires revocation refuses a certificate no current
CRL covers, so that the absence of revocation
information is never read as absence of revocation.

Roots and CRLs are named separately. A bundle of
revocation lists is not a set of trust anchors, and
loading one must never be a way of trusting whatever
the other contains.

31. CORE EBNF (ESSENTIAL)
==================================================

  translation-unit ::= { import-decl | declaration | sandbox-decl }

  import-decl ::= "import" string-literal
                  [ "(" id-list ")" | "as" identifier ]
                  [ capability-annotation ] ";"

  sandbox-decl ::= "sandbox" "(" capability-list ")"
                   compound-statement

  declaration ::= [ "pub" ] (function-def | type-def
                  | behavior-def | instance-def
                  | annotation declaration)

  annotation   ::= capability-annotation
                 | "@needs" "(" instance { "," instance } ")"

  behavior-def ::= "behavior" Identifier "(" type-param-list ")"
                   "{" prototype { prototype } "}"

  prototype    ::= type identifier "(" [ parameter-list ] ")" ";"

  instance-def ::= Identifier "(" type-list ")" "="
                   ( identifier
                   | "{" "." identifier "=" identifier
                     { "," "." identifier "=" identifier } "}" ) ";"

  instance     ::= Identifier "(" type-list ")"

  function-def ::= type identifier "(" [ parameter-list ] ")"
                   compound-statement

  parameter    ::= type identifier [ "=" expression ]

  type-def     ::= "type" identifier [ "(" type-param-list ")" ]
                   "=" type-body ";"

  // The body of a type declaration is a product (a record), a sum (one
  // or more variants), a constraint, or a single type (an alias).
  type-body    ::= product-body | sum-body | constraint-body | type

  product-body ::= "{" product-field { product-field } "}"
  product-field ::= type identifier ";"

  // A sum type's variant payload is ZERO or more types: a bare `V` carries
  // none, `V(T)` carries one, and `V(T1, T2, ... Tn)` carries n. Every
  // payload position is an ordinary `type`, so it may be concrete
  // (`Int`, `UInt(8)`, `List(Str)`) or a generic parameter (`T`), and the
  // positions are independent — `V(T, Int)` and `V(List(T), T)` are
  // well-formed. There is no tuple type, so a variant with n > 1 payload
  // is the way to carry several values of unrelated types as one.
  sum-body     ::= variant { "|" variant }
  variant      ::= identifier [ "(" type { "," type } ")" ]

  // A constraint body refines one type with a predicate, written either
  // after brackets or after `where`.
  constraint-body ::= type [ "[" expression "]" | "where" expression ]

  type-param-list ::= type-param { "," type-param }
  type-param  ::= identifier | "rt" identifier

  spawn-expression ::= "spawn" "(" capability-list ")"
                       compound-statement

  match-expression ::= "match" expression
                       "{" match-arm { "," match-arm } "}"

  // An arm pattern is a variant with a binding for EVERY payload position,
  // or with none: `V(a, b, c)` or `V`. A partial list (`V(a)` on a
  // two-payload `V`) is an error, so a pattern says which variant it is
  // and never discards part of it. `_` is the wildcard arm and must be
  // last; the arms must otherwise cover every variant.
  match-arm    ::= pattern "=>" expression
  pattern      ::= variant-pattern | "_"
  variant-pattern ::= identifier [ "(" identifier { "," identifier } ")" ]

  for-in-statement ::= "for" "(" type identifier "in" expression ")"
                       statement

  primary ::= identifier | literal | "(" expression ")"
            | "rt" expression | f-string | raw-string | byte-string
            | list-literal | map-literal | struct-literal
            | provider-call | spawn-expression | "#location"

  // An f-string's holes are parsed as expressions in place; their format
  // spec (spec §14.1) is a list of flags in any order, of which only the
  // width may be written without its name.
  f-string      ::= "f" '"' { f-string-text | f-hole } '"'
  f-string-text ::= character | "{{" | "}}"
  f-hole        ::= "{" expression [ ":" format-spec ] "}"

  format-spec   ::= format-item { "," format-item }
  format-item   ::= int                       // the width
                 | "." int                    // the precision
                 | flag [ format-argument ]
  flag          ::= "width" | "left" | "right" | "center"
                 | "fill" | "zero" | "plus" | "space" | "minus"
                 | "hex" | "oct" | "bin" | "upper" | "lower"
                 | "group" | "precision"
                 | "auto" | "decimal" | "scientific" | "percent"
                 | "trim"
  format-argument ::= int | char | quoted-string

  range-expression ::= expression ".." expression
                     | expression "..=" expression

  slice-expression ::= primary "[" range-expression "]"

  type ::= identifier [ "(" type-list ")" ]
         | "rt" type
         | "Int" "(" int ")" | "UInt" "(" int ")"
         | "Float" "(" int ")" | "Dec" "(" int ")"
         | "Str" "(" int ")" | "Bytes" "(" int ")"
         | "List" "(" type-list ")"
         | "ISize" | "USize"

  // "List" "(" T ")" is the heap List; "List" "(" T "," int ")"
  // with an integer-literal second parameter is List(T, N) (§44).
  // A "List" whose second parameter is not an integer literal is
  // an error.

33. ARTIFACTS AND CODE GENERATION
==================================================

Native binary / object files via LLVM, plus CBOR
sidecars: the knowledge graph and the residual notes.
Residuals become LLVM thunks carrying computation,
provenance, and capabilities.

Lowering reads only the residual part of the graph (§3.4)
and records a lowered edge for each node it emits:

  - each emitted code range is mapped to the id of the node
    it lowers;
  - each residual binding and parameter is mapped to its
    runtime location (register, stack slot, or thunk field)
    over the code ranges where it is live.

The map may be carried in the graph's lowered table or
in the binary's debug information (for example DWARF line
and variable-location entries keyed by node id); a
debugger shall be able to resolve both. When it is carried
in DWARF, each line-table row's (file, line, column) is
the span start of the node it lowers, and a row at column
0 is its function's entry; variables are named as their
binding or parameter nodes. The binary
records the content hash of its graph artifact, so a
debugger can check that the two match.
Debug and check profiles always emit the graph. Release
builds may omit it; if they do, they omit the hash too.
The hash is the global `resid_graph_hash`, 32 bytes.

Debug builds carry DWARF: a subprogram per function and,
per statement, a line entry at the statement's source line
and column, which every instruction of the statement uses.
A debugger maps a location to nodes through the graph's
spans; specialized functions keep their originals' lines.
Parameters and bindings of Int, Bool, Float, Str and
pointer type are local variables, located by their
values; a module function is named without its module
prefix.

In the graph artifact, a node's knowledge is `known` for
literals and for literal structure over them (negation,
parentheses, casts, lists, `Some`), `effect` for a node
that performs an effect itself, and `residual` otherwise.
An effect is named `stdout` or `stderr` for printing and
`family.verb` for a provider call, whose family is also
the node's capability. Derive rules name the reduction
step: fold, known (a binding's value), beta, eval (a pure
builtin), select (an arm chosen by a known condition),
unwrap, interpolate, concat, specialize, comptime,
accumulate (the in-place string rewrite) and rebuild (a
node copied because a child was reduced). A derived node
has the type and def of the node it derives from.

Range facts are computed per function over its immutable
bindings: from integer literals, the operators + - * / %
and &, lengths (in [0, 2^47]), `for` over a range, and the
comparisons of dominating if and while conditions,
including an if whose branch always returns, breaks or
continues; `x != 0` makes x nonzero. A + - * / or % whose
operand ranges, within their types, prove it cannot
overflow or divide by zero (or compute MIN / -1) is
lowered without its check. A list's length is known from
a list literal, and `i < xs.len()` holds for i inside
`for (i in a..xs.len())` and under a condition
`i < xs.len()`; an index `xs[i]` with i >= 0 and below the
length is lowered without its bounds check. A match arm
or pattern gives a RESIDUAL scrutinee its variant (tag),
and a binding of a struct literal gives its references
the field nodes (fields). The artifact lists these as
facts of RESIDUAL nodes, with the discharged and check
facts of debug builds.

33.1  Signed Provenance

Every binary carries signed provenance: a COSE_Sign1
(RFC 9052, tag 18, alg EdDSA -8, protected header with
kid) over a Provenance payload (§34). It is appended to
the binary as a trailer:

  [code][COSE_Sign1][cose length: u32 BE]["RESIDPROV2"]

The code hash covers the bytes before the trailer. The
payload binds the source, the binary and every sidecar by
hash, so one signature covers them all; a sidecar whose
hash does not match is rejected, not trusted. A detached
copy of the COSE_Sign1 may also be written as
<artifact>.resid-prov.cbor.

The payload may be concealed: the COSE_Sign1 payload is
then a COSE_Encrypt0 (alg ChaCha20-Poly1305, 24) of the
Provenance map, with deterministic nonces so builds stay
reproducible.

Release builds require a signing key and fail without
one. Debug builds without a key are unsigned: they carry
no trailer and the compiler reports it as a note.

`resid verify <binary>` checks the signature against the
keyring (§28.3), the code hash, and the hash of each
sidecar present, and then reports the record in two
parts. EVIDENCE is what the verifier re-derived itself:
the code hash, each sidecar's hash, the detached copy
(byte-equal to the trailer when present), whether the
compiler running `verify` is the one recorded, the graph
artifact's sources and the capabilities its nodes use
(which must lie within the grant), and the source hashes
when `--sources DIR` names a tree to hash. ATTESTATION is
what only the signer says: toolchain, profile, output
name, grant, and the sources without `--sources`. The
two are never collapsed into one answer.

The key that verified the signature is named by where it
came from: `anchored` ($RESID_HOME/keys, the install's
keyring), `supplied` (`--pub`, `RESID_VERIFY_PUB`) or
`local` (keys/*.pub in the current directory, which is
not an anchor: whoever wrote that directory could have
put the key there). `--anchored` accepts only an anchored
key. (Implementation status: the graph tools do not
verify on their own; run `residc verify` first.)

The implementation may employ any target ISA extensions
(AVX-512, NEON, SVE, etc.) for code generation and for
the realization of wide numeric types.

34. CBOR SCHEMAS
==================================================

Provenance, Capability, ResidualNotes, ResidualNote,
KnowledgeCache, CacheEntry — as previously defined
(RFC 8949 preferred serialization).

KnowledgeGraph (CDDL):

  graph    = { version: 1, source: [* file], nodes: [* node],
               roots: roots, ? lowered: [* lowering] }
  file     = { path: tstr, hash: bstr }
  roots    = { source: [* id], residual: [* id] }
  node     = { id: id, kind: tstr, type: tstr,
               knowledge: "known" / "effect" /
                          "residual" / "invalid",
               ? name: tstr, ? value: any, deps: [* id],
               ? def: id,
               ? seq: id, effects: [* tstr],
               capabilities: [* tstr], span: span,
               ? derive: { from: id, rule: tstr },
               ? reason: { kind: tstr, ? dep: id,
                           ? detail: tstr },
               ? facts: [* fact], ? doc: [* tstr],
               hash: bstr }
  fact     = { kind: tstr, ? lo: int, ? hi: int,
               ? zero: bstr, ? one: bstr, ? tag: tstr,
               ? nodes: [* id] }
  span     = [file-index: uint, line: uint, col: uint,
              end-line: uint, end-col: uint]
  lowering = { node: id, symbol: tstr, lo: uint, hi: uint,
               ? loc: [* location] }
  location = { lo: uint, hi: uint, where: tstr }
  id       = uint

A declaration or a use (function, parameter, binding,
reference, call, field) carries its name, so tools can
answer queries by symbol. Offsets in lowering are
relative to the symbol. Nodes
created by reduction have the span of the node they
derive from. Every RESIDUAL or EFFECT node has a reason;
its detail is the effect for effect and the budget that
ran out (fuel, steps, memory, depth, specs) for budget, and dep names
the first RESIDUAL operand or definition for unknown.

Provenance (CDDL; the COSE_Sign1 payload, §33.1):

  provenance = { toolchain: tstr, profile: tstr,
                 sources: [* file], code: bstr,
                 ? graph: bstr, ? notes: bstr,
                 ? cache: bstr, grant: [* tstr],
                 ? native: { * tstr => bstr },
                 output: tstr, ? reduce: tstr,
                 ? compiler: bstr }

Hashes are SHA-256. code is the hash of the binary before
its trailer; graph, notes and cache are the hashes of
those sidecars' bytes; compiler is the hash of the
compiler binary that produced the build; grant is main's
declared authority (§19), one entry per capability as
`family` or `family(readonly)` -- authority enters a
program only at main, so this is the whole program's.
native maps each native module the binary links (§47) to
the SHA-256 of its artifact as given, before the compiler
rewrote it; like grant it is ATTESTATION: the code hash
covers the linked result, and the signer names the
artifact it came from.
reduce names a reduction budget other than the default
(§27), e.g. "unbounded, memory 8192 MB": the budget
decides how much of the program was computed at compile
time, so a rebuild needs the same one to reproduce the
code hash.

ResidualNotes is a projection of the graph: one note for
each residual node, reachable from the residual roots,
that a programmer can act on: an `rt` value
(rt-binding), a provider call (provider-call), and a call
whose reason is budget (fuel, steps, memory or depth),
loop or whistle.
A note is [kind, symbol, line, col, file]: symbol is the
source from the node to the end of its line (at most 40
characters), col is 0-based, and notes are sorted by
file, line and column. The graph's reasons cover every
other RESIDUAL and EFFECT node.

Files:

  <artifact>.resid-graph.cbor
  <artifact>.resid-notes.cbor
  <artifact>.resid-prov.cbor     (detached COSE_Sign1)
  <project>.resid-cache.cbor

==================================================
36. PURE REDUCTION RELATION
==================================================

Κ ⊢ e → e′ covers β-reduction, constant folding,
constraint discharge, provider substitution, behavior
insertion, method desugaring (handles), pattern matching,
destructuring, checked arithmetic, numeric interoperability
widening, string interpolation, range/slice construction,
dead-code elimination (dead-binding elision), check
discharge from facts (§3.2a), and structural identity.

Reduction is performed on the knowledge graph (§3). Each
step adds nodes and derive edges and never deletes a
source node (§3.4), so every reduction the compiler makes
can be traced after the build.

The implementation shall eliminate every residual that
is dischargeable under current knowledge and capabilities.

Integer reduction works at the width the operands are
written at: a shift is a bit operation at its left
operand's width (§6.1), a literal takes the type of the
operand beside it (§6.1a), and the wrapping, saturating
and checked families (§6.5) reduce on known operands of
one integer type. What the evaluator cannot carry stays
residual: a bound past 64 bits (so Bounded's bound for
Int(128) is a call, not a constant), the sum of two
64-bit values, an operation that would overflow or trap,
and a complement above the carried range. Reduced and
unreduced builds therefore agree, value for value.

Float(64) reduces too, and it is carried as the IEEE-754
bit pattern of the value rather than as its text, so a
reduced Float is the double the run time would have
produced: `0.1 + 0.2` reduces to 0.30000000000000004 and
not to 0.3. A literal is read with the same correctly
rounded conversion the run time uses, an integer operand
beside a Float becomes that Float (§6.2), and `+ - * /`
and the six comparisons reduce on known operands. What
stays residual is a division by zero (the run time's to
do), an integer past 2^53 beside a Float (the widening
would round), any other Float width, and a value whose
shortest text is an exponent, since Resid has no
exponent literal to write it as.

Specialization is part of the reduction relation: a call
whose arguments are partly known is replaced by a call to a
copy of the callee reduced under the known arguments (only
the unknown arguments remain parameters). Known fields of
a partly-known composite argument (§3.2a fields) count as
known for specialization. The copy is a new function node
with a specialize derive edge from the original, labelled
with the known-argument pattern. Knowledge is thus
preserved across residual calls (Law 6).

Termination of reduction:

  - A call with all arguments known is evaluated; a pure
    call that re-enters itself with identical arguments is
    left residual immediately, and the budgets of §27
    (steps, fuel, memory, depth) bound the rest. A tail
    call is evaluated in a loop, not nested: it costs no
    depth, and only what it passes on stays live.
  - Specialization terminates by a homeomorphic-embedding
    test on the active chain of specializations of the same
    function with the same known positions: integers embed
    by sign and magnitude, strings by length, other values
    by equality. When an ancestor's known values embed in
    the new call's, the known positions whose values
    changed are generalized (made unknown); an identical
    pattern reuses the specialization in progress.
  - A specialization is kept only when it shrinks the
    callee; implementations may bound the number of
    specializations (reported as a note).

Dead-code elimination is part of the reduction relation:
a binding whose reduced value is a fully-known constant
and whose name is not referenced by the residual
computation that remains shall be elided from the emitted
program. Elision is authorized only when the value is
fully known; a binding whose value remains residual —
because its evaluation could perform an effect, abort,
or fail to converge — is preserved even when
unreferenced. Runtime behavior may not depend on the
presence or absence of an elided binding.


==================================================
37. DEBUGGING AND TOOLING
==================================================

Debug artifacts: the CBOR knowledge graph and the
residual notes projected from it.

“Why is this residual?” is a tooling query (IDE / resid
why), not a language construct.

Canonical debug structure: the knowledge graph artifact
(§3, §34). Tools and debuggers answer questions by walking
it, never by re-analyzing source:

  - Static: for any source span, symbol or node, show its
    knowledge state, value or facts, and the chain of
    derive edges back to source ("what was reduced, by
    which rule, and why"), or the reason it stayed
    residual.
  - Live: a debugger attached to a running binary maps
    the program counter to a node through the lowered
    edges, reads residual bindings from their recorded
    locations, and shows the KNOWN nodes that were
    folded into the running code, with their values. It
    steps by node (seq edges order effects), not only by
    source line.

`resid why` accepts a symbol, file:line, or node id and
reports both what was reduced (derive edges, with rules)
and what stayed residual (reasons, missing facts).

Normative tooling expectations:

  residc          – compiler driver
  resid fmt       – canonical formatter
  resid-notes     – residual-notes viewer
  resid-cache     – knowledge-cache inspector
  resid-graph     – knowledge graph and dependency
                    graph viewer
  resid why       – reduction and residual provenance
                    query
  resid debug     – graph-aware debugger (static and
                    live)
  resid verify    – package signature verification
  resid test      – test runner: one file, or every
                    *_test.resid under a root
  LSP surface     – residual status, capabilities,
                    knowledge state, doc comments,
                    exhaustiveness diagnostics,
                    sandbox attenuation view

A `test` block is an entry point, like `main`: the
compiler discovers it at compile time, generates the
entry point that runs it, and the file is built as its
own program (SPEC-testing.md §1.1). `residc test` runs
one file, or with no file every `*_test.resid` under a
root; its exit status is 0 when every test passed, 1
when a test ran and failed, and 2 when a file did not
compile, so a broken file is never read as a failing
test. A test declares the capabilities it uses with
`@requires` on the block, and is bound by the same
ceiling as any other function (§20).

41. RESOLVED DECISIONS (CARRIED FORWARD)
==================================================

Float representations, provider volatility, spawn
scheduler, doc-comment storage, and incremental-cache
granularity remain as decided in earlier versions.

v3.1: wide binary floating point is capped at
Float(128). Float(256)/Float(512) are removed from
the type system; arbitrary precision is carried by
the Dec(N) decimal family (§6.6a).

v3.2: integer operator result widths amended
(§6.1). Addition/subtraction/division/remainder/
shifts/bitwise yield the widest operand width;
overflow is a checked error, never a static type
promotion. Only multiplication keeps the range
rule. Integer literal typing is specified in new
§6.1a. Widen-then-narrow emission and silent
truncation at bindings are forbidden (§6.4).
Rationale: the previous range rule inflated types
without preserving values — implementations widened
arithmetic then truncated the carry at the binding,
losing exactly the bit the promotion existed to
protect. Under checked-by-default arithmetic,
reducing the check away when operand values are
provable (and trapping otherwise) preserves the
safety guarantee while keeping types predictable.

v3.3: fixed-capacity value types Str(N), Bytes(N), and
List(T, N) are added to the core type system (new §44).
They are nominal types with a statically known extent;
the compiler may place them inline in the frame and may
never heap-allocate them. Binding literals adopt the
annotated capacity when they fit; oversized literals are
compile-time errors (never silently truncated). Extent is
changed only by an explicit cast — a bounded copy that
truncates on the right when narrowing. Fixed strings and
byte arrays re-type to Str / Bytes over a NUL-terminated
view, and the runtime built-in functions accept them
wherever a Str / Bytes is declared.


v3.4: numeric soundness pass; the implementation now
matches every rule below.
  - Multiplication follows the same width rule as the
    other operators (widest operand, checked); the
    range rule is removed. It widened types without a
    matching guarantee: products were bound back to
    the operand width and wrapped silently.
  - Checked arithmetic covers + - * / % at every width,
    including division by zero and MIN / -1.
  - Signed `>>` is arithmetic; shift counts that are
    negative or >= the width are specified.
  - Unsigned operands compare, divide and take the
    remainder as unsigned.
  - Explicit conversions are checked; wrapping_iN /
    wrapping_uN conversions added for bit-level code.
  - Literal adoption (6.1a) stated precisely, including
    wide targets; if/match arms must agree in type.
  - Str(N) capacity is N UTF-8 bytes; casts never split
    a codepoint; Str(N) indexing is checked against the
    content.
  - The `null` literal is removed (it contradicted the
    no-null non-goal and was never implemented).
  - Reduction (§27, §36): specialization on partly-known
    arguments, termination by homeomorphic embedding,
    deterministic budgets reported as notes.

v3.5: the knowledge graph (§3) is made normative and
observable. v3.4 and earlier stated that programs "are
represented as" a graph but gave no contract, and the
self-hosted compiler worked on source text with no graph.
  - The graph is the sole IR between parsing and lowering.
  - Node fields, knowledge-state rules, edge kinds (operand,
    def, seq, derive, lowered), derivation rules and
    residual reasons are defined (§3.1–3.5).
  - Facts (§3.2a) add partial knowledge to RESIDUAL nodes
    (range, bits, length, fields, tag, path, ...); reduction
    uses them to discharge checks and select arms.
  - Reduction is provenance-preserving graph rewriting
    (§36); specialization records its pattern.
  - The graph is emitted as <artifact>.resid-graph.cbor
    (§33, §34) with a code-range and runtime-location map,
    so debuggers walk it both statically and live (§37).
  - Residual notes are a projection of the graph.
  - `&&` and `||` short-circuit (§30); the relative
    precedence of & ^ | and of && || is spelled out.
  - Signed provenance is specified (§33.1, §34): one
    COSE_Sign1 trailer binds the source, the binary code
    and every sidecar (graph, notes, cache) by hash, with
    optional COSE_Encrypt0 concealment. Release builds
    require a key. Package signatures use the same
    envelope (§28.1). Earlier versions named a Provenance
    schema without defining it.

v3.6: linear builders (§45). StrBuf and ListBuf(T) build a
string or a list by appending in place into one growing
buffer. Each builder value must be used exactly once, which
is what makes the in-place append unobservable.
  - filesystem.sha256 and filesystem.append_bytes (§32).
  - filesystem.write_hex and append_hex (§32); the graph
    artifact's knowledge states, effect names and derive
    rules, and the `resid_graph_hash` global (§33).

v3.7: vector types (§46). Vec(T, N) holds N lanes of a
numeric width in registers, with lanewise arithmetic,
comparisons to lane masks Vec(Bool, N), select, shuffles and
lane-order reductions. The builtin sqrt (§6.7) also takes a
Float vector.

v3.8: fixed-capacity builders (§45.2). StrBuf(N), BytesBuf(N)
and ListBuf(T, N) fill a Str(N), Bytes(N) or List(T, N) in
its own storage; overflow is recorded and try_finish reports
it as a value.
  - b.discard() gives a builder up; a `?` may leave with
    region-backed builders unconsumed, never with a StrBuf
    (§45.1).
  - .capacity() on fixed-capacity values, Bytes(N).len() is
    N, fixed lists and byte strings display as values, and
    `[]` adopts an expected List(T, N) (§44.3).

v3.9: `xs.with(i, x)` on List(T) and List(T, N) (§17, §44.3):
the list with element i replaced, checked like `xs[i]`. It is
the verb vectors already use for a lane (§46.1), so one name
means "this value with one element different" across the
three sequence types. The update is in place when the old
list is dead, decided by the same linear analysis as Map
updates; it is never observable.

v3.10: Fixed-capacity values (§44) are stored inline, in a
frame or inside the value holding them, never in heap
storage of their own. A result or a loop's carried value is
copied when its frame ends; the casts to Str and Bytes copy
the text, since the heap value may outlive the frame.

v3.11: native modules (§47). `@link("m")` binds a function
to code compiled from another language. Its calls are
effects of the family native_m and run in a process that
holds no authority at all. Manifest ceilings (§21.1) now
compare modes, bound a dependency's own dependencies by
its ceiling, and take the meet when a dependency is
declared twice; package archives carry .ll artifacts
(§28.1) and the provenance record names them (§34).

42. NUMERIC INTEROPERABILITY SUMMARY
==================================================

  - Every width is a distinct first-class type.
  - No subtyping and no implicit narrowing; value-
    preserving widening is implicit at bindings,
    returns and fields.
  - Integer literal typing follows 6.1a: a literal
    adopts the other operand's type or the declared
    type of the position it wholly fills, else the
    smallest fitting signed width >= 64.
  - Every integer operator yields the widest operand
    width. + - * / % are checked at every width
    (overflow, division by zero, MIN / -1 trap).
  - Shifts and bitwise operators are unchecked bit
    operations; signed `>>` is arithmetic.
  - Explicit conversions are checked; wrapping_iN /
    wrapping_uN keep the low bits.
  - Argument expressions match parameter types
    exactly after literal adoption.
  - Widen-then-narrow code is forbidden; carries are
    never silently discarded.
  - Signed/unsigned mix is a hard error.
  - Integer + float yields the float type.
  - Float + float yields the wider float.
  - Dec(N) op Dec(M) yields Dec(max(N, M)).
  - Mixing Dec with Int/UInt/Float is a hard error.
  - Dec has no NaN/Inf; invalid operations are errors.
  - Checked arithmetic is the default; wrapping and
    saturating variants are explicit.
  - Behaviors Eq/Ord/Hash are generic over the family.


==================================================
43. SANDBOXING SUMMARY
==================================================

  - Manifest supplies the capability ceiling per
    dependency.
  - Source may only further restrict (import annotation
    or sandbox block).
  - Enforcement is static when possible, residual
    otherwise.
  - Transitive closure is fully attenuated.
  - Handles enter a sandbox only if their capabilities
    are ≤ the sandbox.
  - Knowledge-cache writes from a sandbox are limited
    to entries whose capabilities fit the sandbox.
  - Every function's uses are granted by its @requires
    or its sandbox; authority starts at main (§20).
  - A native module is a family of its own (native_<m>);
    its code runs in a process the kernel confines to
    computation (§47), so the family grants no other
    authority.


==================================================
44. FIXED-CAPACITY VALUE TYPES
==================================================

Fixed-capacity value types carry a statically known
bound on their extent. Storage is fixed and known at
compile time, so a value is stored inline: in the
activation frame of the function that holds it, or inside
the record, list or other value that contains it. A
value never requires heap allocation of its own; one
that outlives its frame (a result, a value carried to a
loop's next step) is copied, which is not observable.

  Str(N)         a UTF-8 string of at most N bytes;
                 storage N + 1 bytes, NUL-terminated
  Bytes(N)       a byte array of at most N bytes;
                 storage exactly N bytes
  List(T, N)     N elements of type T, stored
                 contiguously; storage N * sizeof(T)

N is a decimal integer literal with N >= 0. Every N is a
distinct nominal type; there is no subtyping between
differing capacities. The non-size List(T) denotes the
ordinary heap List (§32).

Fixed-capacity values are immutable and bind like any
other value (§7). There is no in-place mutation.

--------------------------------------------------
44.1  Binding and Literal Adoption
--------------------------------------------------

A literal whose extent fits the declared capacity may be
bound directly to a fixed-capacity type; the annotation
provides the literal with its expected type:

  Str(8) s = "abc";           // ok — 3 bytes
  Str(2) e = "é";             // ok — 2 bytes
  Bytes(4) b = b"1234";       // ok
  List(Int, 8) xs = [10, 20, 30];
                              // ok — slots 3..7 are
                              // zero-initialized

A literal whose extent exceeds the declared capacity is a
compile-time error. It is never silently truncated:

  Str(4) s = "toolong";       // error — 7 > 4
  Str(2) e = "éé";            // error — 4 bytes > 2
  List(Int, 2) xs = [1, 2, 3];
                              // error — 3 > 2

Fixed lists are dense: the declared capacity N is the
value's extent, and element slots beyond those supplied
by the binding literal are zero-initialized.

--------------------------------------------------
44.2  Casts
--------------------------------------------------

Capacity is changed only by an explicit cast. Casts are
the only operators that may change a fixed capacity.

  Str(N)   -> Str           a heap Str holding the
                            text up to the NUL
  Bytes(N) -> Bytes         a heap Bytes holding the
                            bytes up to the first zero;
                            aborts when a non-zero byte
                            follows a zero one (it would
                            be dropped)
  Str      -> Str(N)        explicit bounded copy;
                            keeps the longest prefix of
                            whole codepoints that fits
                            in N bytes
  Bytes    -> Bytes(N)      explicit bounded copy
  Str(N)   -> Str(M)        explicit bounded copy
  Bytes(N) -> Bytes(M)      explicit bounded copy of
                            min(N, M) bytes, zeros
                            included
  List(T, N) -> List(T)     copies all N dense elements
                            into a heap list; the
                            resulting list's length is N

Widening a capacity copies and pads; narrowing copies and
drops the end of the content, never splitting a UTF-8
codepoint. Truncation never happens apart from an
explicit cast.

A heap-to-fixed list cast (List → List(T, N)) is not
provided.

--------------------------------------------------
44.3  Access
--------------------------------------------------

Indexing a fixed-capacity value is bounds-checked and
aborts on an out-of-range index (resid_index_abort),
identically to heap lists (§17):

  s[i]    // Str(N): Int — the codepoint at index i,
          // checked against the content's codepoint count
  b[i]    // Bytes(N): Int — the byte at i, checked
          // against the capacity N
  xs[i]   // List(T, N): T, checked against N
  xs.with(i, x)
          // List(T, N): equal to xs but for element i,
          // which is x; i checked against N

`.len()` on a List(T, N) or a Bytes(N) is the statically
known capacity N; they carry no dynamic length. `.len()` on
a Str(N) is the codepoint count of its content, as str_len.
`.capacity()` on any fixed-capacity value is N, a
compile-time constant (also in a generic body, where N is a
type parameter).

A List(T, N) displays as its N elements, `[1, 2, 0]`, read
from its storage; a Bytes(N) (and a Bytes) as its literal,
`b"ab\x00"`. An empty literal `[]` adopts an expected
List(T, N), zero-filled, also when N is a type parameter.

--------------------------------------------------
44.4  Interoperability
--------------------------------------------------

Fixed-capacity strings and byte arrays are accepted as
arguments to the runtime built-in functions wherever a
Str or Bytes is declared (println, print, str_len, …).
The passing form is a NUL-terminated view of the inline
buffer: no copy and no heap allocation.

User-defined functions require an exact type match: a
Str(N) argument does not match a Str parameter. Convert
explicitly with the identity cast.

Eq / Ord / Hash behaviors do not extend to fixed-capacity
types; use the heap forms for behaviors requiring them.


==================================================
45. LINEAR BUILDERS
==================================================

Bindings are immutable (§7), so building a string or a list
one piece at a time creates a new value per step. A linear
builder lets that loop append in place instead:

  StrBuf         builds a Str
  ListBuf(T)     builds a List(T)

  StrBuf b0 = StrBuf();
  StrBuf b1 = b0.push("ab");
  StrBuf b2 = b1.push_char('c');
  Str s = b2.finish();                  // "abc"

  ListBuf(Int) l0 = ListBuf();          // T from the binding
  ListBuf(Int) l1 = l0.push(1);
  List(Int) xs = l1.push(2).finish();   // [1, 2]

Operations:

  StrBuf()               an empty StrBuf
  ListBuf()              an empty ListBuf(T); T comes from
                         the expected type, as for []
  b.push(s)              StrBuf: appends a Str; returns the
                         builder
  b.push_char(c)         StrBuf: appends the codepoint c (Int)
  b.push(x)              ListBuf(T): appends x (T, with the
                         usual literal adoption and widening)
  b.finish()             StrBuf -> Str, ListBuf(T) -> List(T)
  b.discard()            gives the builder up (Void); a
                         StrBuf's buffer is freed

--------------------------------------------------
45.1  Linearity
--------------------------------------------------

A builder value is used exactly once. Every operation
consumes its builder, and push returns the builder to use
next. Because no code can observe a builder after it is
used, push may write into the same buffer, and finish hands
that buffer to the result without copying. Push is amortized
O(1), and a doubling buffer needs one allocation.

The rule is checked statically on every binding and
parameter of a builder type (E0401-E0404):

  - E0401: a builder is never consumed on some path. That
    covers a path that reaches the end of its scope, or a
    `return` that does not consume it.
  - E0402: a builder is used twice. Two uses in one
    expression or on one path count, and so does a use
    after it was consumed.
  - E0403: a builder bound outside a loop is used inside
    the loop body, or captured by a lambda.
  - E0404: a builder type appears inside another type (a
    struct field, a List, Map, Set, Option or Result
    element, or a closure type).

Branches (`if`/`else`, `match` arms, `c ? a : b`,
`value else { }`) must consume the same builders, except a
branch that leaves by `return`, `break` or `continue`. The
right operand of `&&` / `||` is conditional, so it must not
consume a builder bound outside it.

A builder that is only passed along (`return b;`, or an
argument to a function taking a builder) counts as one use.
`b.discard()` is a use: it ends a builder on purpose, e.g.
before an early `return`.

A `?` (§14) that returns early leaves the builders still
live on its path unconsumed; they are given up. That is
allowed for builders whose storage the regions reclaim
(ListBuf and the fixed-capacity builders of §45.2). A
StrBuf owns heap memory, so a `?` that could return early
while a StrBuf is live is E0401: finish or discard it
first.

--------------------------------------------------
45.2  Fixed-Capacity Builders
--------------------------------------------------

The fixed-capacity types of §44 have builders that fill
the value in its own storage, with no heap list or string
on the way:

  StrBuf(N)      builds a Str(N)
  BytesBuf(N)    builds a Bytes(N)
  ListBuf(T, N)  builds a List(T, N)

  StrBuf(8) b0 = StrBuf();     // N from the expected type
  Str(8) s = b0.push("ab").push_char(233).finish();

The constructors are StrBuf(), BytesBuf() and ListBuf(),
taking N (and T) from the expected type; BytesBuf() needs
one. Operations:

  b.push(s)              StrBuf(N): appends a Str or Str(M)
  b.push_char(c)         StrBuf(N): appends codepoint c
  b.push(x)              BytesBuf(N): appends byte x
                         (0..255; another value aborts)
  b.push(x)              ListBuf(T, N): appends x
  b.finish()             the value; unfilled storage is
                         zero, as for a literal (§44.1)
  b.try_finish()         Result(V, Int): Ok(the value), or
                         Err(the length the pushes asked
                         for) when they did not fit
  b.discard()            gives the builder up

A push that would pass the capacity writes nothing (a
Str(N) always holds whole codepoints of what fit) and only
records the length asked for. finish() on a builder that
overflowed aborts, like an out-of-range index;
try_finish() reports it as a value, so input that does not
fit is an error rather than a crash. Capacity is in UTF-8
bytes for StrBuf(N) and BytesBuf(N), in elements for
ListBuf(T, N). The rules of §45.1 apply unchanged.

==================================================
46. VECTOR TYPES
==================================================

  Vec(T, N)      N lanes of T, held in registers

T is Int(8), Int(16), Int(32), Int (Int(64)), the same UInt
widths, Float(32) or Float, and N is 2, 4, 8, 16, 32 or 64
(E0410). `Vec` is a builtin type name: a program cannot
declare a type of that name. A comparison yields a lane mask
Vec(Bool, N). A vector is a value like a number: it is
immutable and never shared, and it has no heap part.

  Vec(Float, 4) v = [1.0, 2.0, 3.0, 4.0];   // exactly N
  Vec(Float, 4) h = splat(0.5);             // every lane
  Vec(Int(32), 8) k = lanes();              // 0, 1, .., 7
  Vec(Float, 4) w = v * 2.0 + h;            // lanewise
  Vec(Bool, 4) m = w > 4.0;                 // lane mask
  Float s = select(m, w, h).sum();          // 20.0

A list literal of exactly N elements, splat(x) and lanes()
build a vector; they take its type from the slot they are
written in: a binding's value, a return value or an argument
of a user function (and select's operands). Anywhere else
the vector is bound first (E0412). Numeric literals adopt
the lane type, and must fit it; as for scalars, an integer
literal operand of an operator also meets Float lanes
(v * 2).

--------------------------------------------------
46.1  Operations
--------------------------------------------------

  a + b, a - b, a * b    lanewise; a / b for Float lanes
  a & b, a | b, a ^ b    integer lanes and masks
  ==, !=, <, <=, >, >=   lanewise, a Vec(Bool, N)
  -v, ~v (integers), !m (masks)
  v[i]                   lane i, checked like a list index
  v.with(i, x)           v with lane i replaced (checked)
  v.sum()                lanes added in lane order
  v.shuffle(idx)         lane j is v[idx[j] mod N] (the
                         floor modulo, so -1 is N-1)
  v.wrapping_add(w), wrapping_sub, wrapping_mul
                         integer lanes, wrapping (two's
                         complement)
  m.any(), m.all()       some lane / every lane is true
  m.bits()               an Int with bit i = lane i (for
                         64 lanes, lane 63 is the sign bit)
  select(m, a, b)        a where m is true, else b
  sqrt(v), min(a, b), max(a, b)
                         lanewise (min is a < b ? a : b)
  v.to_list()            the lanes as a List(T)
  (Vec(U, N))v           Int or UInt to Float, Float to
                         Float, or a widening integer
                         conversion (never fails)

The two operands of a binary operator have the same vector
type, or one is a scalar of its lane type (broadcast to
every lane). Integer lanes are checked like integers
(§6.5): +, - and * abort on overflow in any lane; the
wrapping_* methods wrap instead. Integer division is not
defined on vectors. A Float sum adds from lane 0 upward
(-0.0 + v[0] + v[1] + …), so it rounds like the scalar loop
it replaces; an integer sum is checked.

A vector cannot appear inside another type: a List, Map,
Option, Result, struct field, variant payload or closure
type, written or inferred ([v, v], Some(v)) (E0411), and a
lambda or spawn region cannot capture one (E0411); pass it
as an argument instead. An f-string does not show one
directly; interpolate v.to_list().

==================================================
47. NATIVE MODULES
==================================================

A native module is code written in another language and
compiled to LLVM IR text: a library Resid does not have,
or an algorithm already written. A program binds it with
@link and calls it like any function. It changes none of
the laws: a native call is a provider read (Law 8), an
effect (Laws 9, 10) that is never reduced, authorized by a
capability (Law 14), and the native code itself holds no
authority whatever.

--------------------------------------------------
47.1  Binding
--------------------------------------------------

  @link("zlib")
  Int adler32(Bytes(4096) data, Int len) {}

  @requires(native_zlib)
  Int main() { ... adler32(block, n) ... }

  - The argument is one string literal: lowercase
    letters, digits and `_`, starting with a letter, at
    most 32 bytes. It names the module and its family,
    native_zlib.
  - Only on a top-level function that is not generic and
    carries no @requires, @needs, @import or @export
    (E0234). The body is empty, `{}` (E0234): the module
    supplies it. The C symbol is the function's declared
    name.
  - Not in the standard library, the tools or the
    runtime (E0232): they stay Resid.
  - The function's own use is native_<m>, carried to every
    caller by E0219, to spawn lists by E0214 and bounded by
    sandboxes and manifest ceilings (E0211, E0212, E0218)
    exactly like any family. The family has no modes
    (`native_m(readonly)` is refused) and a bare `native`
    is not a family.

--------------------------------------------------
47.2  Types
--------------------------------------------------

Only values with a fixed byte form cross (E0233
otherwise):

  Resid                C parameter       C result
  Bool                 bool              bool
  Int, Int(64)         int64_t           int64_t
  Int(8|16|32)         int8_t ...        int8_t ...
  UInt, UInt(64)       uint64_t          uint64_t
  UInt(8|16|32)        uint8_t ...       uint8_t ...
  Float, Float(64)     double            double
  Float(32)            float             float
  Str(N)               const char *s,    void, with
                       int64_t cap       char *out,
                       (N + 1 bytes,     int64_t cap
                       NUL-terminated)   appended
  Bytes(N)             const uint8_t *b, void, with
                       int64_t cap       uint8_t *out,
                       (exactly N bytes) int64_t cap
                                         appended
  Void                 -                 void

N is at most 16777216. A pointer the native code receives
points into its own copy of the value, never into the
program.

--------------------------------------------------
47.3  Artifacts
--------------------------------------------------

`-native m=<path.ll>` (from [native.m], §35) gives module
m's artifact: LLVM IR text for x86-64 Linux, freestanding
(no C library). Before it is linked it is checked and
rewritten:

  - Every global it references must be its own, an LLVM
    intrinsic, or memcpy, memmove or memset. It may not
    declare or reach anything else, the runtime included.
  - It may not contain module asm, aliases, ifuncs,
    comdats, thread-local or external globals, section or
    partition placement, personality functions, quoted
    names, or definitions of llvm.* globals (constructors
    and used lists): nothing that could run at load time
    or be placed outside its functions.
  - Every symbol it defines is renamed native.<m>.<name>,
    so it can neither replace nor reach a symbol of the
    program, the runtime or another module.

A refusal is E0237. Each @link function must be defined by
its artifact, externally visible (E0235), with exactly the
C types of 47.2 (E0236).

--------------------------------------------------
47.4  Execution
--------------------------------------------------

Each call runs the native function in a fresh process:
the program's own executable, started again with an empty
environment and no descriptor but the call's socket.
Before any native instruction runs, that process disables
the time-stamp counter, unmaps the vDSO clock pages, and
installs a seccomp filter: it may read and write its
socket, map memory that is not executable, and exit.
Anything else (a file, a socket, a clock, a process, a
signal, executable memory) kills it. Its CPU time is
limited to 60 seconds.

The caller sends the arguments, reads the result, and
checks it as untrusted input: a Bool must be 0 or 1, a
narrow integer within its type, a Str(N) valid UTF-8 up
to a NUL within N + 1 bytes. A host that dies, exits
otherwise, or answers malformed fails the call: the
calling thread aborts, which inside a spawn region is the
region's Err(RegionError) (§9, §19).

So a native call:

  - holds no authority beyond native_m itself, and
    native_m grants nothing but computation;
  - sees nothing of the program but its arguments;
  - keeps no state from one call to the next: there is no
    hidden identity (§4), and equal arguments meet the
    same code each time;
  - is never evaluated at compile time.

A call costs a process start (about 2 ms for a small
program).
Native code that needs the OS - a display, a device, a
file - is not a native module; the program does that work
through its providers.

The process boundary contains native code; it does not
make native code correct. The answer is checked for type,
never for meaning.

==================================================
48. SECRET VALUES
==================================================

Secret(T) is a value the program holds but may not observe
through control flow, a memory address or an output. Secrecy
is knowledge (Law 13) carried in the type: every expression
computed from a secret is secret, and the places a value
could leave that knowledge are checked.

  secret(x)               Secret(T) from a T
  declassify(s, "why")    the T back; needs the declassify
                          family (Law 14), a non-empty string
                          literal reason (E0251), and is an
                          effect in the graph artifact
                          (declassify.<reason>)

A secret may: take part in & | ^ with integers; be shifted by
a public amount; go through wrapping_add, wrapping_sub and
wrapping_mul; be read at a public index when it is a list;
be stored in a record field or a list element; be chosen by
ct_select(c, a, b), a mask selection on a Secret(Bool) c
between integers of at most 64 bits or Bools. The result is
secret. A secret list's or text's .len() is public.
lib/crypto.resid's ct_eq compares secret byte lists in
constant time and publishes the one-bit verdict, so it needs
the declassify grant.

The builtin names secret, declassify, classify, secret_split,
secret_join and ct_select are reserved (E0259): a function by
one of those names would replace the builtin in every module,
libraries included.

A secret integer wider than 32 bits may not be stored in a
list, builder, vector, map or set, whether the type is written
or inferred (E0258): the runtime boxes list integers of 2^54
or more, a choice made on the value. Secret byte strings are
UInt(8) lists; wider secrets live in records and parameters.

A secret whose value is known after reduction is refused
(E0250): it would be in the binary for everyone who has it.
A secret(...) written directly inside declassify(...) is
accepted, since that states the value is public.

A secret may not: decide an if, while, match or ternary, or
an && / || operand; be compared, divided or taken a remainder
of; be cast to a type that cannot hold every value; be an
index, a range bound or a shift amount, have a
method called on it other than .len(), be a provider
argument, or be a spawn region's result (E0255); be a Map
key or Set element in any written type (E0253); go
through checked + - *, whose overflow abort is a branch on the
value (E0254); wrap Option, Result, a sum type, Map, Set, a
handle, a function or another secret (E0253); or wrap a Bytes
or Bytes(N), in any written or inferred type (E0253): a heap
Bytes ends at its first zero byte, so its .len() and its
conversions scan the bytes, a branch on each. Secret byte
strings are List(Secret(UInt(8))).

No observation behavior reaches a secret. The structural Show
and Serialize refuse a type that holds one at any depth and
name the field path (E0256). Show, Serialize, Hash, Eq and Ord
are never given for a type whose arguments contain a secret,
whether declared, asked for by a verb, or needed by a generic
function's copy (E0257); a generic function is checked per
concrete copy. A type that holds a secret may declare its own
Show; its body is checked like any function, so it reaches the
secret only through declassify.

After checking and reduction Secret(T) is erased: it lowers
exactly as T, and secret(x) and declassify(x, r) as x.

The declassify grant is also checked at force time, like a
provider call (§21.3): a function, lambda or spawn body that
still declassifies after reduction asks the running thread's
capability frames for `declassify` when it is entered, once
per call (a self-recursive loop is not checked per step), and
aborts with "capability not granted: declassify" when a spawn
list or sandbox ceiling on the stack dropped it -- for
instance a closure, made where the grant holds, run inside a
spawn () or a sandbox without it. Inside a spawn region the
abort fails the region (its RegionError). A declassify the
reducer folded to a known value leaves no code and no check.

A program that handles secrets runs its allocator in secret
mode, switched on before main: every heap, region, thread
stack and thread-local mapping is left out of core dumps,
and memory is zeroed when it is freed or handed back for
reuse (memory returned to the kernel is zero-filled by the
kernel). Registers, the binary's static data and the
process's initial stack are not covered; main runs on its
own thread stack, which is.

secret_split(s) turns a Secret(List(T)) into a
List(Secret(T)), its length public; secret_join(xs) turns it
back. classify(x) lifts a public value into secret
computation and claims no secrecy, so E0250 does not apply.
All three are free at run time.

lib/word.resid's Word(W, B) and Word64(W, B) behaviors let
cryptographic code be written once and instantiated for
public data and secret data (UInt(32)/UInt(64) words, UInt(8)
bytes); lib/sha256g.resid (SHA-256,
HMAC-SHA-256, HKDF-SHA-256) and lib/sha512g.resid (SHA-512,
SHA-384 and their HMACs) are written that way.
lib/chachag.resid (ChaCha20, Poly1305, ChaCha20-Poly1305) is
generic over Word(W, B) and Wide512(P, B), 512-bit integers
for Poly1305 (Int(512) or Secret(Int(512)), kept in
parameters); lib/chacha.resid is its public copy. Its open
publishes one bit through CtSame(B) (lib/crypto.resid), whose
secret instance is ct_eq and so needs the declassify grant.
lib/x25519g.resid (X25519, RFC 7748) is generic over
Wide512(P, B) too: field elements mod 2^255 - 19 in P
parameters, the ladder's swaps as xor masks; lib/x25519.resid
is its public copy. The peer key is public; the all-zero check
on the shared secret goes through CtSame(B), and the public key
of a private key through X25519Pub(B), whose secret instance
declassifies (so both secret copies need the declassify grant).
lib/aesgcmg.resid (AES-128/192/256, GCM with any IV, AES key
wrap) is generic over Word(W, B) and Block128(X, W, B),
128-bit blocks (UInt(128) or Secret(UInt(128)), kept in
records and parameters; round keys are a list of 32-bit
words); lib/aesgcm.resid is its public copy. The AES-NI
rounds and the carry-less multiply (aesni_enc_round,
aesni_enc_last_round, gf128_mul_hw) take secrets, as they run
in constant time, and keep the result secret. GCM open and
key unwrap publish one bit each through CtSame(B).
ct_hide(x) on a secret x keeps it secret, and so does a cast to
an integer type that holds every value of x (the same or a
wider width, or unsigned to a wider signed type); any other
cast of a secret is checked, and so refused (E0255).
lib/p256.resid and lib/p384.resid (P-256 and P-384, generated
by tools/gen_nistp.py) are generic over P256Word(F, B) and
P384Word(F, B), field elements UInt(576)/UInt(832) or their
secrets: key derivation, ECDH, ECDSA signing and its RFC 6979
nonce (over the generic HMACs) are written once, and
lib/ecdsa.resid's ecdsag_*, ec_public_keyg and ecdhg take the
private key as List(B). A signature, a public key and whether
a key is usable are published through the behavior's open
verb, a declassification at secret types, so those secret
copies need the declassify grant; an ECDH result stays secret.
lib/ed25519g.resid (Ed25519 key generation and signing) is
generic over Wide512(P, B) and Word64(W, B), with a masked
double-and-always-add ladder; lib/ed25519.resid is its public
copy. The public key and the signature are published through
Publish(B) (lib/word.resid), whose secret instance declassifies,
so signing with a secret seed needs the declassify grant; the
compiler signs its provenance record that way.
lib/hpkeg.resid (HPKE, RFC 9180: the labeled HKDF over
HKDF-SHA256/384/512, DHKEM(X25519), DHKEM(P-256) and DHKEM(P-384)
over ecdhg / ec_public_keyg, the key schedule in all four modes,
seal, open and export over AES-GCM and ChaCha20-Poly1305) is
generic over the byte type and the behaviors above;
lib/hpke.resid is its public copy, and no suite has a
public-only path. Private keys, the shared secret, the key
schedule's secrets, nonces and plaintexts are secret bytes; the
AEADs take the nonce in B (aes_gcmg_seal_ivb,
chacha20poly1305g_seal_nb), so it stays secret. Derived public
keys go through X25519Pub(B) or the curve's open verb and the
tag verdict through CtSame(B), so the secret copy needs the
declassify grant.
lib/tls.resid's TLS 1.3 key schedule (HKDF-Expand-Label,
Derive-Secret, the early, handshake and master secrets, the
traffic secrets, keys and IVs), Finished and AES-128-GCM record
protection are generic over the byte type (tlsg_*); its
List(Int) API is the public copy. lib/tlsserver.resid and
lib/tlsclient.resid run the secret copy: the x25519 ephemeral
key and shared secret, every secret of the schedule and the
record keys (TlsKeys) are List(Secret(UInt(8))), each record's
nonce (IV xor sequence number) is computed in secret bytes, and
the server's signing key (lib/tlskey.resid) is secret once
parsed. The key share and signature are published by their
primitives; record ciphertext, an authenticated record's
plaintext and the Finished MAC through TlsPublish(B), whose
secret instance declassifies; a record's tag and the peer's
Finished publish one bit through CtSame(B). Every function and
program that runs a TLS handshake or record therefore needs the
declassify grant.

With TLS, every key the cryptography library handles is secret
at run time (step 2 of PLAN-secret-type.md §7). tests/ct takes
its cases from the graph and fails when a library function that
handles a secret has no case (step 3).
