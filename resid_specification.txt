==================================================
RESID LANGUAGE DESIGN DOCUMENT
Version 3.6 — Production Ready
==================================================


LANGUAGE DESIGN CONTEXT
==================================================

Resid is an eager compile-time programming language.
The compiler’s primary obligation is maximal authorized
reduction of first-class knowledge.

Runtime behavior consists solely of the residual computation
that remains after all provable reductions have been performed.

The name Resid denotes this residual core.

The pronunciation /ˈrɛz.ɪd/ (REZ-id) or /ˈriː.zɪd/ (REE-zid) is the correct and standard pronunciation for the name.

Core statement:

    Compilation is maximal authorized reduction
    of first-class knowledge.


==================================================
FUNDAMENTAL LAWS
==================================================

  1. Everything begins as compile-time reducible.
  2. The compiler must reduce all provable computation.
  3. Unknown information must be explicitly introduced.
  4. Residual computation enters through rt.
  5. Compile-time computation cannot depend on unresolved
     residual information.
  6. The compiler preserves knowledge whenever possible.
  7. Residual dependencies should be minimized.
  8. Authorized external knowledge enters through providers.
  9. Knowledge acquisition is an effect.
 10. Effects determine reducibility.
 11. External information has provenance.
 12. Runtime uncertainty is explicit.
 13. Knowledge is first-class.
 14. Authority is never ambient and may only be attenuated,
      never amplified, across trust boundaries.


==================================================
1. KNOWLEDGE IS FIRST-CLASS
==================================================

Knowledge may be represented, transformed, reduced,
composed, serialized, transmitted, and inspected.

Knowledge includes values, types, constraints, proofs,
behaviors, capabilities, provider results, residual
values, and effects.


==================================================
2. EXECUTION MODEL
==================================================

A program is progressively reduced until only irreducible
computations remain. Compilation is knowledge reduction.


==================================================
3. INTERNAL REPRESENTATION — KNOWLEDGE GRAPH
==================================================

Programs are represented as a knowledge graph (enriched
expression DAG). The graph is the compiler's sole
representation between parsing and lowering: name
resolution, type checking, capability checking, reduction
and lowering all read and extend the graph, and no phase
re-reads source text. The graph is observable: it is
emitted as an artifact (§33, §34) and is what debuggers
and tools walk (§37).

3.1  Nodes

Each node has:

  id            NodeId, unique within the artifact and
                deterministic (§3.5)
  kind          what the node computes (literal, reference,
                binding, call, operator, cast, if, match,
                loop, provider call, spawn, function, ...)
  type          its resolved type
  knowledge     its knowledge state (§3.2)
  value         the value, when knowledge is KNOWN
  deps          ordered operand edges
  effects       the effects it may perform
  capabilities  the capabilities it requires
  provenance    where it came from (source span, provider
                result, or a derivation, §3.3)
  doc           attached doc comments, if any

Pure nodes with equal kind, type and operands may be
shared (hash-consed). Nodes with effects are never
shared: each occurrence is its own node.

3.2  Knowledge States

  KNOWN     value fully determined at compile time
  EFFECT    performs an effect; its order is fixed
  RESIDUAL  depends on runtime values; it is lowered
  INVALID   carries a diagnostic; the program is rejected

A node is INVALID if it or any dep is INVALID. Otherwise
it is EFFECT if it performs an effect, KNOWN if it is
pure and reduction determined its value, and RESIDUAL
otherwise. Every RESIDUAL or EFFECT node records why it
was not reduced (§3.4).

3.2a  Facts (Partial Knowledge)

A RESIDUAL or EFFECT node may carry facts: properties that
hold of its runtime value on every execution. Facts are
knowledge (§1); they are sound, never guessed.

  range(lo, hi)     integer value lies in [lo, hi]
  bits(zero, one)   masks of bits known to be 0 / 1
  nonzero           value is not 0
  length(lo, hi)    Str, Bytes, List, Map or Set length
                    lies in [lo, hi]
  fields            per-field (or per-element) node ids;
                    known fields are KNOWN nodes
  tag(V)            sum value is variant V
  unreachable       node is never evaluated
  path(c)           condition node c holds here (from a
                    dominating if, match arm, loop test
                    or assert)

Facts come from literals, types (an Int(8) is in
[-128, 127]), operators, conversions, branch conditions,
asserts and known fields. Reduction uses them to:

  - discharge checks: overflow, division by zero, index
    and slice bounds, conversion range, Str(N) capacity,
    capability checks (§27);
  - select a match arm or if branch under a RESIDUAL
    scrutinee (tag, range, path);
  - fold a projection of a known field out of a RESIDUAL
    composite;
  - specialize on known fields (§36).

A discharged check is recorded as a derive edge with rule
discharge, naming the facts used, so a debugger can show
why a check is absent. When a check cannot be discharged,
it stays and its node's reason names the missing fact.

3.3  Edges

  operand   node → its i-th dep
  def       reference → the binding, parameter or
            function it resolves to
  seq       effect node → the effect that precedes it in
            evaluation order
  derive    result node → the node it replaces, labelled
            with the rule that produced it (§36)
  lowered   node → the code range and runtime location
            emitted for it (§33)

operand, def and seq edges are acyclic, so the graph is
a DAG; recursion appears as a def edge to a function
node, never as a cycle of operand edges.

3.4  Derivation

Reduction (§36) is graph rewriting that preserves
provenance. A rewrite never deletes a node reachable from
a source root. It adds the result node with a derive edge
to the replaced node, labelled with the rule:

  fold, beta, eval, specialize, generalize, dead-arm,
  elide, discharge, provider, behavior, desugar, widen,
  interpolate

A node left RESIDUAL or EFFECT carries a reason:

  unknown(dep)     depends on the named RESIDUAL dep
  effect(e)        performs effect e
  capability(c)    requires capability c that is not granted
  annotated        written with rt / @residual
  budget(kind)     a reduction budget ran out (§27)
  loop             re-entered itself with identical arguments
  whistle          specialization was generalized (§36)

Evaluating a fully known call is recorded as a single eval
derivation. Its internal steps are not graph nodes; they
can be replayed because reduction is deterministic (§27).

Invariants:

  - Every node in the residual program (the part that is
    lowered) is a source node or reaches source nodes
    through derive edges.
  - Every source node is KNOWN, INVALID or lowered, or has
    a derive edge from the node that replaced it.

3.5  Identity

Node ids are assigned in source order and then in
reduction order, so the same compiler emits the same
graph for the same program. Each node also has a content
hash over kind, type and the hashes of its operands; the
knowledge cache (§21.4) and cross-build tools key on the
hash, never on the id.


==================================================
4. VALUE MODEL
==================================================

Values are immutable, have no observable identity, and
may be freely copied. Handles are identity-bearing
runtime resources under capability control. Only handles
may represent mutable state.


==================================================
5. MEMORY MODEL
==================================================

Resid does not expose stack, heap, or register allocation.
The compiler decides storage. The implementation may use
any target ISA extensions (AVX-512, NEON, SVE, …) for
optimization; raw intrinsics are not exposed.

Fixed-capacity value types (§44) carry a statically known
extent, so the compiler may place them inline in the
activation frame; they never require heap allocation.
Storage placement remains an implementation detail — the
program never observes it.


==================================================
6. PRIMITIVE NUMERIC TYPES (FIRST-CLASS)
==================================================

Numeric types are first-class nominal types.

Integer family (distinct types for every width):

  Int(8)   Int(16)   Int(32)   Int(64)
  Int(128) Int(256)  Int(512)

  UInt(8)  UInt(16)  UInt(32)  UInt(64)
  UInt(128) UInt(256) UInt(512)

Aliases (fixed, reproducible):

  Int  = Int(64)
  UInt = UInt(64)

Pointer-sized (target-dependent):

  ISize    // signed, width of a pointer
  USize    // unsigned, width of a pointer

Floating-point family:

  Float(16)  Float(32)  Float(64)  Float(128)

  Float(128) is the widest floating-point type.
  Wider binary floats are not part of the language;
  arbitrary precision is carried by the decimal
  family below.

Alias:

  Float = Float(64)

Arbitrary-precision decimal family:

  Dec(N)    // N significant decimal digits, any N >= 1

Alias:

  Dec = Dec(34)

Each width is a distinct type. There is no subtyping
between any numeric types.


--------------------------------------------------
6.1  Interoperability — Integer Arithmetic
--------------------------------------------------

Mixed-width integer operations are permitted when both
operands are signed or both are unsigned.

Result width: every integer operator — addition,
subtraction, multiplication, division, remainder, and the
bitwise and/or/xor — yields the widest operand width. The
narrower operand is widened (value-preserving) first.

Arithmetic (+ - * / %) is checked (6.5): a result that does
not fit the result type is an error, never a wider type and
never a silently discarded carry. Implementations must not
emit widen-then-narrow sequences that hide a carry.

Shifts:
    The result width is the left operand's width. Shifts
    and bitwise operators are bit operations on the two's-
    complement representation and are not checked: bits
    shifted out are discarded.
    `<<` fills with zeros. `>>` is arithmetic (sign-filling)
    for signed operands and logical for unsigned operands.
    A shift count that is negative or >= the bit width
    yields 0, except that `>>` of a negative signed value
    yields -1 (counts never wrap modulo the width).

Examples:

  Int(8)   + Int(8)   -> Int(8)    // checked; traps on overflow
  UInt(16) + UInt(8)  -> UInt(16)  // widest operand
  Int(256) * Int(256) -> Int(256)  // checked; traps on overflow
  Int(32)  << 4       -> Int(32)
  Int(-8)  >> 1       -> -4        // arithmetic shift

Headroom for a wide answer must be requested explicitly,
by converting one operand up before the operation:

  Int(512) p = (Int(512))a * b;    // a, b : Int(256)

ISize / USize participate with their actual target width.

Signed and unsigned operands may never be mixed in a
single arithmetic operation; an explicit conversion is
required. Unsigned operands use unsigned comparison,
division and remainder.


--------------------------------------------------
6.1a  Integer Literal Typing
--------------------------------------------------

An integer literal takes its type from its context:

  - As an operand of a binary operator whose other operand
    has a concrete integer type, it adopts that type.
  - When it is the whole expression of a binding
    initializer, argument, return value or field, it
    adopts the declared type of that position.
  - Otherwise (for example `1000000 * 1000000`, where both
    operands are literals) it has the smallest signed
    width from {64,128,256,512} that its magnitude fits;
    magnitudes within 64 bits yield plain Int(64).

A literal that does not fit its adopted type is a
compile-time error at every width. Literal adoption does
not reach through `if` / `match` arms: arms must agree in
type (§18), so write `i128(0)` in an arm that must match an
Int(128) arm.


--------------------------------------------------
6.2  Interoperability — Floating-Point
--------------------------------------------------

Integer + floating-point:

  The integer operand is converted to the floating-point
  type of the other operand; the result is that floating-
  point type.

  Int(32) + Float(64)  →  Float(64)

Floating-point + floating-point:

  The result is the wider of the two floating-point types
  (using the order 16 < 32 < 64 < 128).


--------------------------------------------------
6.3  Comparisons
--------------------------------------------------

Relational and equality operators follow the same
widening rules as arithmetic, except that a signed/
unsigned mix is always a hard error.

The result of a comparison is Bool.


--------------------------------------------------
6.4  Assignment and Narrowing
--------------------------------------------------

Narrowing conversions are never implicit.

  UInt(16) x = some_u32;     // hard error
  UInt(16) x = u16(some_u32); // ok (explicit, checked)

Narrowing assignments always require an explicit
conversion. Value-preserving widening is permitted
implicitly at bindings, returns and fields: same
signedness and no narrower, or unsigned into a strictly
wider signed type. Signed into unsigned is never implicit.
Integer literal adoption (6.1a) applies as specified there.

Explicit conversions — the helpers of 6.7 and the cast
(Type)expr — are checked: a value that the target type
cannot represent (too large, too small, negative into
unsigned, or a NaN / out-of-range float into an integer)
is a runtime error. Bit-level truncation is requested
explicitly with the wrapping conversions of 6.7.

Argument expressions must match the parameter's declared
type exactly, after literal adoption. Computed argument
expressions are never implicitly widened or narrowed to
fit a parameter.

Implementations must never emit widen-then-narrow code
around an assignment: if a computed value does not fit
its target type, the program fails, never truncates
silently.


--------------------------------------------------
6.5  Checked Arithmetic
--------------------------------------------------

After operands have been brought to the common result
type, + - * / % are checked at every width (8 through
512 bits). Overflow of the result type, division or
remainder by zero, and signed MIN / -1 are runtime errors
that abort the process (a region's failure inside spawn,
§19). MIN % -1 is 0.

An out-of-range integer literal is a compile-time error
(6.1a). Any other overflow is detected when the operation
executes. Compile-time reduction never folds an
overflowing operation: it leaves it residual, so reduced
and unreduced programs fail identically (§36).

Wrapping and saturating variants (wrapping_add,
saturating_mul, …) are supplied by the standard library
for every width.


--------------------------------------------------
6.6a Decimals — Dec(N) Semantics
--------------------------------------------------

Dec(N) holds an exact decimal value with N
significant decimal digits:

  sign        + or -
  digits      exactly N significant decimal digits
  exponent    i32, range [-1_000_000, +1_000_000]

Dec(N) values have no NaN and no Inf. Division by
zero, exponent-range overflow, and non-integer
Dec-to-Int conversion are errors: compile-time when
provable, residual errors when forced at runtime.

Rounding:

  When a result must be narrowed to N significant
  digits it is rounded half away from zero:

    0.255    ->  0.26     // to 2 digits
    -0.255   ->  -0.26    // to 2 digits

  Additive and multiplicative arithmetic computes
  the exact decimal result, then rounds once. Division
  computes to N + 2 guard digits, then rounds once.

Interoperability:

  Dec(N) op Dec(M)  ->  Dec(max(N, M))

  Mixing Dec with Int, UInt, or Float in either
  direction is a hard error. Conversion is always
  explicit via dN / iN / fN helpers.

  Dec-to-Int conversion requires the value to be
  integral; a fractional part is an error.

Literals:

  1.5m   123.456m   5m

  Decimal literals carry their digits verbatim; they
  never round-trip through binary. The default type
  is Dec(34). Scientific notation is not part of v1
  decimal literals.

Display:

  Dec values print in fixed notation with all N
  significant digits; trailing zeros are preserved.

    Dec(4) 1.5   ->   "1.500"

  The f-string specifier ":." trims trailing zeros:

    f"{x:.}"


--------------------------------------------------
6.6  Behaviors
--------------------------------------------------

Eq, Ord and Hash are supplied for the entire numeric
family by generic behavior definitions. The compiler
instantiates them for every concrete width. Users never
need to declare per-width instances.


--------------------------------------------------
6.7  Conversion Helpers
--------------------------------------------------

  i8 i16 i32 i64 i128 i256 i512
  u8 u16 u32 u64 u128 u256 u512
  f16 f32 f64 f128
  dN            // any N >= 1: exact conversion to Dec(N),
                // from Int (exact) or Str (exact decimal parse)
  isize usize

Plus the ordinary C-style cast (Type)expr. Both are checked
(6.4).

Wrapping conversions keep the low bits of the two's-
complement representation, for bit-level code:

  wrapping_i8 … wrapping_i512
  wrapping_u8 … wrapping_u512

  wrapping_u8(300)    // 44
  wrapping_u64(-1)    // 18446744073709551615


==================================================
7. BINDINGS AND IDENTITY
==================================================

  Type x = expression;

Bindings are immutable. Shadowing is forbidden everywhere.
There are no assignment operators.

Discard:

  _ = expression;


==================================================
8. FUNCTIONS
==================================================

  Ret name(Type1 p1, Type2 p2 = default) {
      body
  }

Defaults must be pure compile-time expressions.
Named arguments are permitted:

  draw(x = 10, y = 20, color = red);

Entry point: Int main().


==================================================
9. RESIDUAL COMPUTATION
==================================================

  Type x = rt expression;
  @residual Type y = expression;

Residual values are first-class knowledge.
Top-level residual force or unwrap failure aborts the
process. Inside a concurrent region, failure is delivered
as Result.

  known(x);        // compile-time hard error if residual
  rt_known(x);     // residual check


==================================================
10. EFFECTS
==================================================

Effects are first-class. They do not appear in signatures;
capabilities (@requires) are the sole authorization surface.


==================================================
11. BEHAVIORS
==================================================

Behaviors are ordinary compile-time knowledge.

  Ord(Int) = ... ;
  sort(values, using = Reverse(Ord(Int)));

Unique behaviors are inserted automatically; ambiguity
requires explicit selection.

Numeric Eq / Ord / Hash are supplied generically for
the whole family (see §6.6).


==================================================
12. TYPES
==================================================

Product:  type Point = { x: Int, y: Int };
Sum:      type Option(T) = Some(T) | None;
Constraint: type Positive = Int[value > 0];
            type Positive = Int where value > 0;

Residual types are permitted. Edge-case rules R1–R5 remain
in force.

Numeric types are first-class (see §6). Fixed-capacity
value types — Str(N), Bytes(N), List(T, N) — are core
types whose storage is statically bounded (see §44).


==================================================
13. PATTERN MATCHING AND DESTRUCTURING
==================================================

  match expression {
      Some(x) => expression,
      None    => expression
  }

Irrefutable destructuring:

  Point { x, y } = p;
  Some(v) = opt;          // hard error if refutable

if-let / while-let:

  if (Some(x) = opt) { ... }
  while (Some(x) = it.next()) { ... }


==================================================
14. LITERALS AND COMPOSITES
==================================================

  42  0x2A  3.14  1.5m  'a'  "hello"  true  false
  [1, 2, 3]   {"a": 1}   Point { x = 1, y = 2 }

  f"hello {name}"
  f"price: {price:.}"
  r"C:\path\file"
  b"bytes"

Literals default to Int / Float / Dec (for m-suffix
decimals); integer literals follow 6.1a. There is no null
literal: absence is Option's None. Width is otherwise
changed only by an explicit conversion.

A literal may adopt a fixed-capacity expected type from an
annotated binding when its extent fits the declared
capacity; an oversized literal is a compile-time error and
is never silently truncated (§44.1).


==================================================
15. RANGES AND SLICING
==================================================

  start..end        // half-open
  start..=end       // closed
  xs[start..end]


==================================================
16. HANDLES AND LIFETIME
==================================================

  with (Type h = expression) { body }
  with (T a = e1, U b = e2) { body }

Method sugar (handles only): h.m(args) ≡ m(h, args).
Immutable views may be shared across regions; mutable
handles must be moved.


==================================================
17. FIELD AND INDEX ACCESS
==================================================

  p.x   xs[i]   m[k]

Indexing is bounds-checked: an out-of-range index aborts the
program with the offending index and length (resid_index_abort);
it never reads out of bounds silently.

Access to a fixed-capacity value is bounds-checked against its
declared capacity and aborts identically on an out-of-range
index (§44.3).

Shift counts that are negative or >= the operand's bit width
yield 0, or -1 for `>>` of a negative signed value (§6.1); they
never wrap modulo the width. This holds for every integer width,
including wide Int(N)/UInt(N).


==================================================
18. CONTROL FLOW
==================================================

Classic C plus:

  for (Type x in xs) { ... }

  if (Some(x) = opt) { ... }
  while (Some(x) = it.next()) { ... }

The arms of an if-expression or match must all have the
same type (numeric aliases such as Int and Int(64) are the
same type). Arms are not implicitly widened to a common
type.


==================================================
19. CONCURRENCY
==================================================

Structured concurrency:

  Result(T, RegionError) r = spawn (cap1, cap2) {
      return value;
  };

Rules:

  - Capabilities listed explicitly; child ≤ parent.
  - Child receives a fresh CapEnv.
  - Residual forcing uses only the child’s CapEnv.
  - Returns pure values or residuals.
  - Mutable handles moved; immutable views shareable.
  - Child failure → Err(RegionError) to parent.
  - Nested spawn permitted.
  - Scheduler implementation-defined.
  - Work may run in parallel; completion is structured.


==================================================
20. CAPABILITIES AND SECURITY
==================================================

No ambient authority. Capabilities form a lattice and
travel with effects, handles, and residuals. Revocation
is monotonic within an execution / region.

Authority may only be attenuated across trust boundaries;
it may never be amplified.


==================================================
21. SANDBOXING AND LIBRARY ATTENUATION
==================================================

A program may restrict the capabilities available to a
third-party library or any untrusted region of code.

--------------------------------------------------
21.1  Policy Ceiling (Manifest)
--------------------------------------------------

The project manifest supplies the maximum set of
capabilities any dependency may receive:

  [dependencies.http]
  path = "vendor/http"
  capabilities = ["filesystem(readonly)", "network"]

This is a ceiling. Source code may only further restrict;
it may never enlarge the set.

--------------------------------------------------
21.2  Source-Level Attenuation
--------------------------------------------------

Capabilities may be narrowed at the import site or with
an explicit sandbox:

  import "http.resid" (get, post)
      @requires(filesystem(readonly));

  sandbox (filesystem(readonly)) {
      // all code and transitive imports herein
      // see only the listed capabilities
  }

--------------------------------------------------
21.3  Enforcement
--------------------------------------------------

  - When a required capability is statically apparent
    and exceeds the sandbox, compilation fails with a
    hard error.
  - When the requirement is dynamic or residual, the
    call remains residual and fails at force time with
    a capability error.
  - Transitive dependencies are closed under the same
    sandbox; attenuation applies to the entire closure.
  - A handle may enter a sandbox only when every
    capability it requires is ≤ the sandbox’s set.
    Otherwise the program is rejected at compile time
    or the handle use becomes a residual capability
    error.

--------------------------------------------------
21.4  Knowledge Cache Interaction
--------------------------------------------------

Sandboxed compilation may read the global knowledge
cache. It may write cache entries only when the
capabilities associated with those entries are ≤ the
sandbox’s granted set.

==================================================
27. RUNTIME OPTIMIZATION AND MINIMIZATION
==================================================

The implementation shall reduce every provable
computation. It shall not retain residual work that can
be discharged under the granted capabilities and the
available knowledge cache.

Residual notes should make remaining residual work
visible so that later compilations, with additional
knowledge, can eliminate it.

The compiler’s primary performance obligation is
therefore:

  1. Maximize compile-time reduction.
  2. Minimize the residual surface that reaches runtime.
  3. Lower only what remains to efficient native code
     (LLVM).

The reduction outcome is deterministic: budgets count
evaluation steps, calls and allocations, never time, so a
given compiler reduces a given program the same way every
time. Program meaning never depends on a budget: reduced
and unreduced programs have identical observable
behavior, and a budget only decides how much work is left
residual. Every budget that leaves work residual is
reported as a compiler note ("note: reduce: ...").

Release builds may omit diagnostic metadata from residual
thunks. Capability checks may be elided when the required
set is statically known to be present for the relevant
lifetime. Pure prefixes of residual graphs should be
evaluated at compile time whenever possible.


==================================================
28. PACKAGES, SIGNATURES, AND INTEGRITY
==================================================

A package is a directory containing resid.toml, source
files (*.resid), and optional knowledge-cache /
residual-notes artifacts.

Distribution units are content-addressed archives.

--------------------------------------------------
28.1  Package Signature
--------------------------------------------------

Every published package carries a cryptographic
signature over:

  - package name and version
  - content hash of the entire source tree
  - dependency hashes
  - declared capability requirements
  - provenance of any included knowledge-cache entries
  - the public key identity of the publisher

The signature is a COSE_Sign1 (§33.1) over a CBOR map of
these fields, stored alongside the package
(<package>.resid-sig) or inside the archive manifest.

--------------------------------------------------
28.2  Verification
--------------------------------------------------

Before a package is accepted into a build:

  1. The content hash is recomputed and must match.
  2. The signature must verify against a trusted key
     (project keyring or explicitly pinned keys).
  3. All dependency hashes must match the resolved
     artifacts.
  4. Required capabilities must be grantable under the
     current manifest policy.

Failure of any check rejects the package.

--------------------------------------------------
28.3  Key Management
--------------------------------------------------

Projects maintain a keyring of trusted publisher keys.
Keys may be pinned per dependency. Unsigned packages
are rejected unless the project explicitly allows them
under a development profile.


==================================================
29. SURFACE SYNTAX SUMMARY
==================================================

  // numeric types are first-class
  UInt(8) a = u8(1);
  UInt(16) b = u16(2);
  UInt(32) c = a + b;          // a + b : UInt(16), widened on binding

  // sandboxing
  import "http.resid" @requires(filesystem(readonly));
  sandbox (filesystem(readonly)) { … }

  // functions with defaults and named args
  Ret f(Type a, Type b = 0) { … }
  f(1, b = 2);

  // bindings
  Type x = expression;
  @residual Type y = expression;
  Point { x, y } = p;
  _ = expression;

  // residual
  rt expression

  // capabilities
  @requires(filesystem, git(readonly))

  // concurrency
  spawn (cap1, cap2) { body }

  // types
  type T = { f: Type };
  type T = A(Type) | B;
  type T = U[P];
  type T = Int(32);
  Str(8) s = "abc";                // fixed-capacity (§44)
  Bytes(4) b = b"1234";
  List(Int, 8) xs = [1, 2, 3];

  // strings
  f"hello {name}"
  r"raw"   b"bytes"

  // ranges & slices
  0..n   0..=n   xs[1..3]

  // control
  if / while / for / for-in / match / return / break / continue
  if (Some(x) = opt) { … }

  // resources
  with (T a = e1, U b = e2) { … }

  // modules
  import "file.resid";
  import "file.resid" (a, b);
  import "file.resid" as M;
  pub declaration

  // sugar & helpers
  value?    value else { … }
  assert / rt_assert / known / rt_known
  comptime_print / todo / unimplemented
  i32(42)  u64(n)  f32(x)  usize(len)   // checked
  wrapping_u8(x)                        // keeps low bits
  #location

30. OPERATORS AND PRECEDENCE
==================================================

  1. Primary        id literal (e) rt e call index field method
                    range slice
  2. Unary          + - ! ~ (Type)e
  3. Multiplicative * / %
  4. Additive       + -
  5. Shift          << >>
  6. Relational     < <= > >=
  7. Equality       == !=
  8. Bitwise AND    &
  9. Bitwise XOR    ^
 10. Bitwise OR     |
 11. Logical AND    &&
 12. Logical OR     ||
 13. Conditional    e ? e : e
 14. using          e, using = behavior

No assignment operators.
No pure-value method chaining or pipeline operator.

Levels 8–10 bind tighter than 11 and 12: `a | b & c` is
`a | (b & c)` and `a || b && c` is `a || (b && c)`.

`&&` and `||` short-circuit: the right operand is
evaluated only when the left does not decide the result
(`false && e` and `true || e` never evaluate e, including
its effects and aborts). Reduction may therefore fold
them from the left operand alone.

Numeric operators obey the interoperability rules of §6.

33. ARTIFACTS AND CODE GENERATION
==================================================

Native binary / object files via LLVM, plus CBOR
sidecars: the knowledge graph and the residual notes.
Residuals become LLVM thunks carrying computation,
provenance, and capabilities.

Lowering reads only the residual part of the graph (§3.4)
and records a lowered edge for each node it emits:

  - each emitted code range is mapped to the id of the node
    it lowers;
  - each residual binding and parameter is mapped to its
    runtime location (register, stack slot, or thunk field)
    over the code ranges where it is live.

The map may be carried in the graph's lowered table or
in the binary's debug information (for example DWARF line
and variable-location entries keyed by node id); a
debugger shall be able to resolve both. The binary
records the content hash of its graph artifact, so a
debugger can check that the two match.
Debug and check profiles always emit the graph. Release
builds may omit it; if they do, they omit the hash too.

33.1  Signed Provenance

Every binary carries signed provenance: a COSE_Sign1
(RFC 9052, tag 18, alg EdDSA -8, protected header with
kid) over a Provenance payload (§34). It is appended to
the binary as a trailer:

  [code][COSE_Sign1][cose length: u32 BE]["RESIDPROV2"]

The code hash covers the bytes before the trailer. The
payload binds the source, the binary and every sidecar by
hash, so one signature covers them all; a sidecar whose
hash does not match is rejected, not trusted. A detached
copy of the COSE_Sign1 may also be written as
<artifact>.resid-prov.cbor.

The payload may be concealed: the COSE_Sign1 payload is
then a COSE_Encrypt0 (alg ChaCha20-Poly1305, 24) of the
Provenance map, with deterministic nonces so builds stay
reproducible.

Release builds require a signing key and fail without
one. Debug builds without a key are unsigned: they carry
no trailer and the compiler reports it as a note.

`resid verify <binary>` checks the signature against the
keyring (§28.3), the code hash, and the hash of each
sidecar present. Debuggers and tools verify before
trusting a graph or notes artifact, and report an
unverified one as untrusted.

The implementation may employ any target ISA extensions
(AVX-512, NEON, SVE, etc.) for code generation and for
the realization of wide numeric types.

34. CBOR SCHEMAS
==================================================

Provenance, Capability, ResidualNotes, ResidualNote,
KnowledgeCache, CacheEntry — as previously defined
(RFC 8949 preferred serialization).

KnowledgeGraph (CDDL):

  graph    = { version: 1, source: [* file], nodes: [* node],
               roots: roots, ? lowered: [* lowering] }
  file     = { path: tstr, hash: bstr }
  roots    = { source: [* id], residual: [* id] }
  node     = { id: id, kind: tstr, type: tstr,
               knowledge: "known" / "effect" /
                          "residual" / "invalid",
               ? value: any, deps: [* id], ? def: id,
               ? seq: id, effects: [* tstr],
               capabilities: [* tstr], span: span,
               ? derive: { from: id, rule: tstr },
               ? reason: { kind: tstr, ? dep: id,
                           ? detail: tstr },
               ? facts: [* fact], ? doc: [* tstr],
               hash: bstr }
  fact     = { kind: tstr, ? lo: int, ? hi: int,
               ? zero: bstr, ? one: bstr, ? tag: tstr,
               ? nodes: [* id] }
  span     = [file-index: uint, line: uint, col: uint,
              end-line: uint, end-col: uint]
  lowering = { node: id, symbol: tstr, lo: uint, hi: uint,
               ? loc: [* location] }
  location = { lo: uint, hi: uint, where: tstr }
  id       = uint

Offsets in lowering are relative to the symbol. Nodes
created by reduction have the span of the node they
derive from.

Provenance (CDDL; the COSE_Sign1 payload, §33.1):

  provenance = { toolchain: tstr, profile: tstr,
                 sources: [* file], code: bstr,
                 ? graph: bstr, ? notes: bstr,
                 ? cache: bstr, grant: [* tstr],
                 output: tstr }

Hashes are SHA-256. code is the hash of the binary before
its trailer; graph, notes and cache are the hashes of
those sidecars' bytes; grant is the capability set the
build ran under.

ResidualNotes is a projection of the graph: one note for
each RESIDUAL or EFFECT node in the residual roots, with
its reason.

Files:

  <artifact>.resid-graph.cbor
  <artifact>.resid-notes.cbor
  <artifact>.resid-prov.cbor     (detached COSE_Sign1)
  <project>.resid-cache.cbor

36. PURE REDUCTION RELATION
==================================================

Κ ⊢ e → e′ covers β-reduction, constant folding,
constraint discharge, provider substitution, behavior
insertion, method desugaring (handles), pattern matching,
destructuring, checked arithmetic, numeric interoperability
widening, string interpolation, range/slice construction,
dead-code elimination (dead-binding elision), check
discharge from facts (§3.2a), and structural identity.

Reduction is performed on the knowledge graph (§3). Each
step adds nodes and derive edges and never deletes a
source node (§3.4), so every reduction the compiler makes
can be traced after the build.

The implementation shall eliminate every residual that
is dischargeable under current knowledge and capabilities.

Specialization is part of the reduction relation: a call
whose arguments are partly known is replaced by a call to a
copy of the callee reduced under the known arguments (only
the unknown arguments remain parameters). Known fields of
a partly-known composite argument (§3.2a fields) count as
known for specialization. The copy is a new function node
with a specialize derive edge from the original, labelled
with the known-argument pattern. Knowledge is thus
preserved across residual calls (Law 6).

Termination of reduction:

  - A call with all arguments known is evaluated; a pure
    call that re-enters itself with identical arguments is
    left residual immediately, and step / depth / fuel /
    memory budgets bound the rest.
  - Specialization terminates by a homeomorphic-embedding
    test on the active chain of specializations of the same
    function with the same known positions: integers embed
    by sign and magnitude, strings by length, other values
    by equality. When an ancestor's known values embed in
    the new call's, the known positions whose values
    changed are generalized (made unknown); an identical
    pattern reuses the specialization in progress.
  - A specialization is kept only when it shrinks the
    callee; implementations may bound the number of
    specializations (reported as a note).

Dead-code elimination is part of the reduction relation:
a binding whose reduced value is a fully-known constant
and whose name is not referenced by the residual
computation that remains shall be elided from the emitted
program. Elision is authorized only when the value is
fully known; a binding whose value remains residual —
because its evaluation could perform an effect, abort,
or fail to converge — is preserved even when
unreferenced. Runtime behavior may not depend on the
presence or absence of an elided binding.

37. DEBUGGING AND TOOLING
==================================================

Debug artifacts: the CBOR knowledge graph and the
residual notes projected from it.

“Why is this residual?” is a tooling query (IDE / resid
why), not a language construct.

Canonical debug structure: the knowledge graph artifact
(§3, §34). Tools and debuggers answer questions by walking
it, never by re-analyzing source:

  - Static: for any source span, symbol or node, show its
    knowledge state, value or facts, and the chain of
    derive edges back to source ("what was reduced, by
    which rule, and why"), or the reason it stayed
    residual.
  - Live: a debugger attached to a running binary maps
    the program counter to a node through the lowered
    edges, reads residual bindings from their recorded
    locations, and shows the KNOWN nodes that were
    folded into the running code, with their values. It
    steps by node (seq edges order effects), not only by
    source line.

`resid why` accepts a symbol, file:line, or node id and
reports both what was reduced (derive edges, with rules)
and what stayed residual (reasons, missing facts).

Normative tooling expectations:

  residc          – compiler driver
  resid fmt       – canonical formatter
  resid-notes     – residual-notes viewer
  resid-cache     – knowledge-cache inspector
  resid-graph     – knowledge graph and dependency
                    graph viewer
  resid why       – reduction and residual provenance
                    query
  resid debug     – graph-aware debugger (static and
                    live)
  resid verify    – package signature verification
  LSP surface     – residual status, capabilities,
                    knowledge state, doc comments,
                    exhaustiveness diagnostics,
                    sandbox attenuation view

41. RESOLVED DECISIONS (CARRIED FORWARD)
==================================================

Float representations, provider volatility, spawn
scheduler, doc-comment storage, and incremental-cache
granularity remain as decided in earlier versions.

v3.1: wide binary floating point is capped at
Float(128). Float(256)/Float(512) are removed from
the type system; arbitrary precision is carried by
the Dec(N) decimal family (§6.6a).

v3.2: integer operator result widths amended
(§6.1). Addition/subtraction/division/remainder/
shifts/bitwise yield the widest operand width;
overflow is a checked error, never a static type
promotion. Only multiplication keeps the range
rule. Integer literal typing is specified in new
§6.1a. Widen-then-narrow emission and silent
truncation at bindings are forbidden (§6.4).
Rationale: the previous range rule inflated types
without preserving values — implementations widened
arithmetic then truncated the carry at the binding,
losing exactly the bit the promotion existed to
protect. Under checked-by-default arithmetic,
reducing the check away when operand values are
provable (and trapping otherwise) preserves the
safety guarantee while keeping types predictable.

v3.3: fixed-capacity value types Str(N), Bytes(N), and
List(T, N) are added to the core type system (new §44).
They are nominal types with a statically known extent;
the compiler may place them inline in the frame and may
never heap-allocate them. Binding literals adopt the
annotated capacity when they fit; oversized literals are
compile-time errors (never silently truncated). Extent is
changed only by an explicit cast — a bounded copy that
truncates on the right when narrowing. Fixed strings and
byte arrays re-type to Str / Bytes over a NUL-terminated
view, and the runtime built-in functions accept them
wherever a Str / Bytes is declared.


v3.4: numeric soundness pass; the implementation now
matches every rule below.
  - Multiplication follows the same width rule as the
    other operators (widest operand, checked); the
    range rule is removed. It widened types without a
    matching guarantee: products were bound back to
    the operand width and wrapped silently.
  - Checked arithmetic covers + - * / % at every width,
    including division by zero and MIN / -1.
  - Signed `>>` is arithmetic; shift counts that are
    negative or >= the width are specified.
  - Unsigned operands compare, divide and take the
    remainder as unsigned.
  - Explicit conversions are checked; wrapping_iN /
    wrapping_uN conversions added for bit-level code.
  - Literal adoption (6.1a) stated precisely, including
    wide targets; if/match arms must agree in type.
  - Str(N) capacity is N UTF-8 bytes; casts never split
    a codepoint; Str(N) indexing is checked against the
    content.
  - The `null` literal is removed (it contradicted the
    no-null non-goal and was never implemented).
  - Reduction (§27, §36): specialization on partly-known
    arguments, termination by homeomorphic embedding,
    deterministic budgets reported as notes.

v3.5: the knowledge graph (§3) is made normative and
observable. v3.4 and earlier stated that programs "are
represented as" a graph but gave no contract, and the
self-hosted compiler worked on source text with no graph.
  - The graph is the sole IR between parsing and lowering.
  - Node fields, knowledge-state rules, edge kinds (operand,
    def, seq, derive, lowered), derivation rules and
    residual reasons are defined (§3.1–3.5).
  - Facts (§3.2a) add partial knowledge to RESIDUAL nodes
    (range, bits, length, fields, tag, path, ...); reduction
    uses them to discharge checks and select arms.
  - Reduction is provenance-preserving graph rewriting
    (§36); specialization records its pattern.
  - The graph is emitted as <artifact>.resid-graph.cbor
    (§33, §34) with a code-range and runtime-location map,
    so debuggers walk it both statically and live (§37).
  - Residual notes are a projection of the graph.
  - `&&` and `||` short-circuit (§30); the relative
    precedence of & ^ | and of && || is spelled out.
  - Signed provenance is specified (§33.1, §34): one
    COSE_Sign1 trailer binds the source, the binary code
    and every sidecar (graph, notes, cache) by hash, with
    optional COSE_Encrypt0 concealment. Release builds
    require a key. Package signatures use the same
    envelope (§28.1). Earlier versions named a Provenance
    schema without defining it.

v3.6: linear builders (§45). StrBuf and ListBuf(T) build a
string or a list by appending in place into one growing
buffer. Each builder value must be used exactly once, which
is what makes the in-place append unobservable.
  - filesystem.sha256 and filesystem.append_bytes (§32).

42. NUMERIC INTEROPERABILITY SUMMARY
==================================================

  - Every width is a distinct first-class type.
  - No subtyping and no implicit narrowing; value-
    preserving widening is implicit at bindings,
    returns and fields.
  - Integer literal typing follows 6.1a: a literal
    adopts the other operand's type or the declared
    type of the position it wholly fills, else the
    smallest fitting signed width >= 64.
  - Every integer operator yields the widest operand
    width. + - * / % are checked at every width
    (overflow, division by zero, MIN / -1 trap).
  - Shifts and bitwise operators are unchecked bit
    operations; signed `>>` is arithmetic.
  - Explicit conversions are checked; wrapping_iN /
    wrapping_uN keep the low bits.
  - Argument expressions match parameter types
    exactly after literal adoption.
  - Widen-then-narrow code is forbidden; carries are
    never silently discarded.
  - Signed/unsigned mix is a hard error.
  - Integer + float yields the float type.
  - Float + float yields the wider float.
  - Dec(N) op Dec(M) yields Dec(max(N, M)).
  - Mixing Dec with Int/UInt/Float is a hard error.
  - Dec has no NaN/Inf; invalid operations are errors.
  - Checked arithmetic is the default; wrapping and
    saturating variants are explicit.
  - Behaviors Eq/Ord/Hash are generic over the family.

  - Source may only further restrict (import annotation

44. FIXED-CAPACITY VALUE TYPES
==================================================

Fixed-capacity value types carry a statically known
bound on their extent. Storage is fixed and known at
compile time, so the compiler may place values inline in
the activation frame; they never require heap allocation.

  Str(N)         a UTF-8 string of at most N bytes;
                 storage N + 1 bytes, NUL-terminated
  Bytes(N)       a byte array of at most N bytes;
                 storage exactly N bytes
  List(T, N)     N elements of type T, stored
                 contiguously; storage N * sizeof(T)

N is a decimal integer literal with N >= 0. Every N is a
distinct nominal type; there is no subtyping between
differing capacities. The non-size List(T) denotes the
ordinary heap List (§32).

Fixed-capacity values are immutable and bind like any
other value (§7). There is no in-place mutation.

--------------------------------------------------
44.1  Binding and Literal Adoption
--------------------------------------------------

A literal whose extent fits the declared capacity may be
bound directly to a fixed-capacity type; the annotation
provides the literal with its expected type:

  Str(8) s = "abc";           // ok — 3 bytes
  Str(2) e = "é";             // ok — 2 bytes
  Bytes(4) b = b"1234";       // ok
  List(Int, 8) xs = [10, 20, 30];
                              // ok — slots 3..7 are
                              // zero-initialized

A literal whose extent exceeds the declared capacity is a
compile-time error. It is never silently truncated:

  Str(4) s = "toolong";       // error — 7 > 4
  Str(2) e = "éé";            // error — 4 bytes > 2
  List(Int, 2) xs = [1, 2, 3];
                              // error — 3 > 2

Fixed lists are dense: the declared capacity N is the
value's extent, and element slots beyond those supplied
by the binding literal are zero-initialized.

--------------------------------------------------
44.2  Casts
--------------------------------------------------

Capacity is changed only by an explicit cast. Casts are
the only operators that may change a fixed capacity.

  Str(N)   -> Str           identity retype over the
                            NUL-terminated buffer
  Bytes(N) -> Bytes         identity retype
  Str      -> Str(N)        explicit bounded copy;
                            keeps the longest prefix of
                            whole codepoints that fits
                            in N bytes
  Bytes    -> Bytes(N)      explicit bounded copy
  Str(N)   -> Str(M)        explicit bounded copy
  Bytes(N) -> Bytes(M)      explicit bounded copy
  List(T, N) -> List(T)     copies all N dense elements
                            into a heap list; the
                            resulting list's length is N

Widening a capacity copies and pads; narrowing copies and
drops the end of the content, never splitting a UTF-8
codepoint. Truncation never happens apart from an
explicit cast.

A heap-to-fixed list cast (List → List(T, N)) is not
provided.

--------------------------------------------------
44.3  Access
--------------------------------------------------

Indexing a fixed-capacity value is bounds-checked and
aborts on an out-of-range index (resid_index_abort),
identically to heap lists (§17):

  s[i]    // Str(N): Int — the codepoint at index i,
          // checked against the content's codepoint count
  b[i]    // Bytes(N): Int — the byte at i, checked
          // against the capacity N
  xs[i]   // List(T, N): T, checked against N

`.len()` on a List(T, N) is the statically known capacity
N; a fixed-capacity list carries no dynamic length.

--------------------------------------------------
44.4  Interoperability
--------------------------------------------------

Fixed-capacity strings and byte arrays are accepted as
arguments to the runtime built-in functions wherever a
Str or Bytes is declared (println, print, str_len, …).
The passing form is a NUL-terminated view of the inline
buffer: no copy and no heap allocation.

User-defined functions require an exact type match: a
Str(N) argument does not match a Str parameter. Convert
explicitly with the identity cast.

Eq / Ord / Hash behaviors do not extend to fixed-capacity
types; use the heap forms for behaviors requiring them.


==================================================
45. LINEAR BUILDERS
==================================================

Bindings are immutable (§7), so building a string or a list
one piece at a time creates a new value per step. A linear
builder lets that loop append in place instead:

  StrBuf         builds a Str
  ListBuf(T)     builds a List(T)

  StrBuf b0 = StrBuf();
  StrBuf b1 = b0.push("ab");
  StrBuf b2 = b1.push_char('c');
  Str s = b2.finish();                  // "abc"

  ListBuf(Int) l0 = ListBuf();          // T from the binding
  ListBuf(Int) l1 = l0.push(1);
  List(Int) xs = l1.push(2).finish();   // [1, 2]

Operations:

  StrBuf()               an empty StrBuf
  ListBuf()              an empty ListBuf(T); T comes from
                         the expected type, as for []
  b.push(s)              StrBuf: appends a Str; returns the
                         builder
  b.push_char(c)         StrBuf: appends the codepoint c (Int)
  b.push(x)              ListBuf(T): appends x (T, with the
                         usual literal adoption and widening)
  b.finish()             StrBuf -> Str, ListBuf(T) -> List(T)

--------------------------------------------------
45.1  Linearity
--------------------------------------------------

A builder value is used exactly once. Every operation
consumes its builder, and push returns the builder to use
next. Because no code can observe a builder after it is
used, push may write into the same buffer, and finish hands
that buffer to the result without copying. Push is amortized
O(1), and a doubling buffer needs one allocation.

The rule is checked statically on every binding and
parameter of a builder type (E0401-E0404):

  - E0401: a builder is never consumed on some path. That
    covers a path that reaches the end of its scope, or a
    `return` that does not consume it.
  - E0402: a builder is used twice. Two uses in one
    expression or on one path count, and so does a use
    after it was consumed.
  - E0403: a builder bound outside a loop is used inside
    the loop body, or captured by a lambda.
  - E0404: a builder type appears inside another type (a
    struct field, a List, Map, Set, Option or Result
    element, or a closure type).

Branches (`if`/`else`, `match` arms, `c ? a : b`,
`value else { }`) must consume the same builders, except a
branch that leaves by `return`, `break` or `continue`. The
right operand of `&&` / `||` is conditional, so it must not
consume a builder bound outside it.

A builder that is only passed along (`return b;`, or an
argument to a function taking a builder) counts as one use.
